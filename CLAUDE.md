## Application: ThoughtAuction (Aukce myšlenek)

**Purpose:** A website with several publication boards (categories) where anyone can post their own contribution and pay to push it higher up the board.

**Boards and posts**

- The core of the app is a simple, clear, infinitely scrolling page of user posts, ordered by their current value (highest first). There are several boards (categories); each one is its own such page.
- A post has only a **title and a text of at most 2048 characters including spaces**. **No author is shown**, only the title, the text and the post's current value.
- **Post value** = paid amount (1 USD = 10 points) + resonances (1 user's agreement = 1 point) - age (1 day = 1 point).
- Posting, creating a new category and expressing resonance are **for signed-in users only**. Reading is public.
- **Resonance**: a user can give one resonance to a given post only once. Nobody sees who resonated - not even the post's author - only the count.
- A post's author can **pay for it repeatedly**; payments accumulate, so each new payment raises the value by the amount paid.
- Appearance is deliberately plain: no colors, just a bold title and the message. The post form is text only, with emoji support.
- A **category** has a title (the slug is generated from the title; on a collision a sequence number is appended) and a short description of at most 4096 characters including spaces.
- When a category is created, a **machine evaluation (machine rules) of the category** is produced - algorithmically first and later also by an AI model - used afterwards to compare whether a post matches the category's intent. An administrator can view and edit these machine rules.
- System pages: **Terms** (rules and conditions), **GDPR** and **Contact**.

**Moderation**

- An administrator can mark a post as violating the public rules and delete it with **no refund** of the payment. If a user has more violating posts within a given period (stated in the rules and controlled by a parameter), the **account is blocked and all of the user's posts are removed without compensation**.
- Violation checking has three levels:
  1. **Algorithmic** (local) - evaluates a post, and a category's title and description, *before publication and before the payment is confirmed*. If it does not meet the rules, the user gets a message that publication is not allowed.
  2. **AI model via API** - the content is sent to an AI model to be judged against the rules. **Not in the first development version**: only the preparation for the call is built, as a **mock**, with no real model connected yet.
  3. **Manual, by an administrator** - can find any post and block it with a stated reason, which is sent to the author and shown as an in-app notification.
- The local algorithm returns a **violation score in %**: above 30 % the user is shown a notice that they should edit the post; above 50 % the content is shown as potentially violating and may be blocked without refund on closer review; above 75 % it is violating and publication is not allowed.
- It also checks **whether the post matches the topic of its category** (against the category's machine rules). The same thresholds apply to the mismatch score: above 30 % an edit is recommended, above 50 % potential risk, above 75 % not allowed.
- When a category or post is judged violating, the author is shown a message with the reason and the specific aspects behind it.
- In scope for the first version: the local algorithms for posts and categories, and the AI-call preparation as a mock only.

**Implemented so far - the `boards` module: boards, posts, resonance and moderation (no payments yet)**

- Backend `app/modules/boards/` and frontend `src/modules/boards/`, enabled in both `modules.json` files; its settings (`page_size`, points per USD / resonance / day of age) live in `backend/modules/boards.json`. UI and routes call boards *categories* (`/categories`, `/categories/:slug`, `/categories/new`); the slug comes from the title (`slugify`/`unique_slug` in `service.py`, `-2`, `-3` ... on a collision, `new` is reserved).
- **A post's value is computed on read** (`service.post_value`) and never stored. The listing orders by `service.rank_expression` instead - paid points + resonance points + `points_per_day` x created-time-in-days - which gives the same order as the value at any moment (the `now` term is the same for every post and cancels out), so page boundaries stay stable between loads. Posts with equal shown values come in arbitrary but stable order. Don't "simplify" it into a per-row age computation in SQL.
- `Post.paid_cents` is in the schema and the formula, but **nothing writes it until payments are built** (it is 0 today); tests set it directly. Payments will need the `stripe_payment_gate` module's purposes and a ledger.
- **Authors are never exposed**: `Post.author_id` / `Category.created_by_id` are stored for moderation only, `PostOut` / `CategoryOut` omit them, and who resonated is only ever a row in `module_boards_resonances` (composite primary key = once per user and post; `resonance_count` is denormalized and moved in the same transaction). A viewer sees only their own `resonated_by_me`. The public listing uses the module's `get_optional_user`, which treats an invalid or expired token as anonymous - the frontend sends its stored token on every request, so a 401 there would log a visitor out of a page that needs no login.
- Text limits are fixed constants, not config (changing one needs a migration): post title 120 (our choice - the spec gave none), post text 2048, category title 120, description 4096. They count characters (code points), so an emoji is one; the frontend mirrors them in `boards/api.ts` (`charCount`) and its textareas deliberately have no `maxLength` (it counts UTF-16 units).
- **Moderation** (`app/modules/boards/moderation/`, `admin_router.py` under `/manage`, UI at `/moderation`), three levels:
  1. *Local* - `scorer.py` (violation score in percent from a small cs/en `lexicon.py` plus shape heuristics, each aspect a probability combined as independent signals, seeing through spaced-out letters / digits / stretched letters) and `topic.py` (mismatch against the category's **machine rules** - keywords built from its title and description, stored in `Category.machine_rules`, editable by administrators). A percent must be strictly *above* `warn_percent` / `risk_percent` / `block_percent` (30 / 50 / 75, `ModerationConfig` in `boards.json`) for the level "warn" / "risk" / "blocked". The topic score is deliberately **damped by confidence** (distinct words in the post, keywords in the rules): lexical matching is weak evidence, so a short post or a sparsely described category can at most advise, never hard-block - tune `topic_*` in `boards.json` before loosening it.
  2. *AI model* (`ai.py`) - **prepared, not connected**: request, prompt, response schema and a validating parser exist, only `MockAiModerator` is wired in (`get_ai_moderator()` is the one place to swap it, and `ai_review_enabled` is off). Any failure of the AI call is ignored - the local checks have already run.
  3. *Manual* - an administrator (`User.is_admin`, never the auth role) blocks a post with a reason: `status="blocked"`, removed without refund (`paid_cents` is left untouched - there is no refund path), the author gets a notification through the `notifications` module (i18n keys `boards:notification.*`, in this module's own locale bundle).
- **The gate**: every new post or category is assessed first (`router.enforce`) - 422 `moderation_blocked` above the block threshold, 409 `confirmation_required` at risk level unless the request has `confirm_risk: true` - and `POST .../check` returns the same verdict without writing anything, which is what the frontend shows before publishing. The scores and findings are stored with the post (`Post.assessment`) for the administrator. When payments are built, this check must run **before a payment is confirmed**.
- **Strikes**: a blocked post counts as a strike; `strike_limit` of them within `strike_period_days` (3 / 30 in `boards.json` - state the same numbers in the public rules) block the account (`User.is_blocked`) and take its remaining published posts down as `removed` - which are not strikes themselves. A blocked account fails every write with 403 `account_blocked` (`deps.get_active_user`) but can still read; the frontend learns it from `GET /me` (`useBoardsMe`). Unblocking sets `User.strikes_reset_at`, so earlier violations stop counting. Only `published` posts are public: listings, counts and resonating all filter on it.
- **Terms, GDPR, Contact**: the pages are the existing modules switched on, not new code. Terms ("Pravidla a podmínky", `/obchodni-podminky`), Privacy (`/ochrana-osobnich-udaju`), About and Cookies are `stripe_payment_gate`'s legal pages - enabled in the *frontend* `modules.json` only, since the payments backend stays off until payments are built - and Contact (`/kontakt`) is `kontaktni_formular` on both sides (`CONTACT_MAIL` per server in `.env`, reply texts in `backend/modules/kontaktni_formular.json`). The Terms and Privacy texts in `legalLocales.ts` are rewritten for ThoughtAuction (content rules, the checks and thresholds, strikes, anonymous authors, the value formula, no refund for a blocked post, Art. 22 GDPR wording for the automatic account block) - a divergence from the template's e-shop texts, so expect a merge conflict there whenever `core` touches that file. The numbers the texts quote come from `public/legal.json`'s `params` (a small generic addition to `legal.ts`), and `tests/test_modules_boards_legal.py` fails if they stop matching `boards.json` / the models - change a threshold, the strike rule, a limit or a point factor and update `params` and the effective date together.
- **Before going live**: fill `provider` (name, IČO, address, email) and `effectiveFrom` in `legal.json` (the pages show a warning banner until then); have a lawyer read the Terms and Privacy - they are drafts, in particular the no-refund clause, the 14-day withdrawal / immediate-performance wording, the licence to display content, the identity-disclosure rule and the retention periods; when the AI moderator is connected, update Terms (the checks) and Privacy (a new recipient, a transfer, the automated-decision wording); when payments are built, enable `stripe_payment_gate` on the backend too and work through its README's checklist.
- Not built yet: payments (and the cumulative top-up), a real AI model, administrators blocking a *category* or restoring a blocked post, "my posts".
- Testing note: `app.modules.boards.router` as a dotted string resolves to the `APIRouter` (the package re-exports `router`), so monkeypatch module attributes through `sys.modules["app.modules.boards.router"]`. Local dev DB: `thoughtauction_db` (the shared `backend/.env` may still point at another app's - override `DATABASE_URL` per command).

## Repository purpose

This repository hosts a **family of applications built on one shared core**, rather than a single deployable app. The reusable foundation — `backend/` (FastAPI), `frontend/` (Vite/React), and `scripts/` (build + deployment tooling), wired to a separate, shared authorization service at `auth.withfbraun.com` (see "Authorization" below, which is the largest and most actively-evolving part of it) — is developed on the `core` branch. Each application lives in its own branch and pulls in `core`'s changes, so a fix or feature that belongs to every app is made once, on `core`, instead of being duplicated per application. Components remain independently versioned and deployed within any given branch — see "Independent versioning" below.

### Branch structure

- **`core`** — the shared foundation described by the rest of this file (backend, frontend, scripts, auth integration). Cross-cutting work happens here first.
- **Application branches** — one per real app, branched **directly from `core`** (the `new-app` skill automates this). They diverge with app-specific code (models, pages, config) while periodically merging in updates from `core`.
- **`template_app`** — also branched from `core` and kept in sync with it, but *not* the fork point for the applications above. It carries forward the repository's original, standalone template role: a generically-branded starting point for cloning and renaming into a one-off app outside this family. Don't confuse the two workflows.

**Branches synced from `core`:** `template_app`, `slavickovy-knihohratky`, `api-hub`. This list grows as applications are added — the `new-app` skill appends to it automatically when it forks one; the `new-module` skill reads it (not a hardcoded branch list) to know where to roll a new module out to. Keep it current if a branch is added or retired by hand.

When working on a branch other than `core`, treat app-specific code you find as intentional local divergence — don't "fix" it back to match `core` unless that's the actual task.

## Workflow requirements

- **Commit after every change.** Once a change (feature, fix, config edit) is complete and working, create a git commit for it before moving on to the next one.
- **Every backend change needs test coverage.** After adding or modifying anything under `backend/app/`, create or update the matching test(s) under `backend/tests/` in the same change — do not leave backend code changes untested.
- **Every frontend change must pass `npm run build`** (`tsc` + `vite build`) before being considered done; UI-visible changes should also be exercised in a browser, not just typechecked.
- **New source files get the standard header** — see "File headers" below for the exact text and placement rules.
- **Every change updates release news.** Prepend a short, user-facing bullet describing the change to `backend/release_news.json`'s `unreleased` array (backend changes) or `frontend/public/release_news.json`'s (frontend changes), in the same commit as the change itself. `scripts/build.py` seals these into a dated, versioned release at build time — see Deployment below.

## Architecture

### Backend: config, routing, DB, logging, email
- All settings load through `app/config.py`'s `Settings` (pydantic-settings), sourced from `backend/.env` (see `.env.example`). `BASE_DIR` there anchors all relative paths (env file, log dir) to `backend/` regardless of the process's cwd. `get_settings()` is `@lru_cache`d — a running process never picks up `.env` changes without a restart (`uvicorn --reload` only watches `.py` files, not `.env`).
- All REST routes are mounted under the `/api` prefix via `app/api/router.py`, which aggregates sub-routers (`app/api/public/version.py`, `app/api/auth/router.py`, `app/api/account/router.py`). Add new endpoints as their own `APIRouter` and wire them into `api_router` there, rather than adding routes directly in `main.py`.
- DB access is async-only: SQLAlchemy's async engine + `asyncpg` (the `DATABASE_URL` scheme is `postgresql+asyncpg://`, which has no sync counterpart — don't reach for `psycopg2`-style sync sessions). `app/models/base.py` has an empty `Base`; `app/models/user.py`'s `User` is the only concrete model so far (see Authorization below) — holds just the identity link (`auth_sub`) plus fields genuinely local to this app (an illustrative `nickname` — see the local account resource below — and `is_admin`, see below). Identity fields (email, name, role, ...) stay owned by the auth service and are read fresh from the JWT / `GET /api/auth/me`, never duplicated here.
- Alembic is wired for the async engine (`alembic init -t async`). `alembic/env.py` pulls the connection string from `Settings.database_url`, not from the static placeholder in `alembic.ini`, and sets `prepend_sys_path = %(here)s` so `import app` resolves regardless of invocation directory. Any new model must be imported in `alembic/env.py` (see the `from app.models.user import User` line there) or autogenerate won't see its table.
- Logging is configured once at import time in `main.py` via `configure_logging()` (`app/logging_config.py`) — a `TimedRotatingFileHandler` (fixed daily rotation, `when="midnight"`) + console handler attached to the root logger. Settings field names match `.env.example`'s `LOGGING_*` keys exactly: `logging_level`, `logging_dir`, `logging_filename`, `logging_days_history` (backup count), `logging_message_format`. Note `.env`/`.env.example`'s format string's `\t` is a literal backslash-t (two characters), not an actual tab — `.env` files don't interpret string escapes the way Python source does, and `Settings` passes the value straight to `logging.Formatter()` unmodified. That's a property of the configured value, not a bug to fix in code; change it in `.env` (to a real tab or something else) if the literal `\t` in log output isn't wanted.
- Email goes through `app/services/email.py`'s `send_email()`, built on `fastapi-mail`. Connection defaults come from `Settings` (`MAIL_*` in `.env`), but every `ConnectionConfig` field can be overridden per call via kwargs (e.g. a one-off `MAIL_FROM`). `MAIL_SUPPRESS_SEND=true` still builds and dispatches the message internally (so tests can assert on it via `FastMail(...).record_messages()`), it just skips opening a real SMTP connection.

### Backend: authorization (auth.withfbraun.com)
This template doesn't implement its own user auth — it's a **backend-for-frontend proxy** in front of a separate, shared auth service. The browser only ever talks to this app's own `/api/auth/*`; only this backend holds the `X-Api-Key` secret and talks to `auth.withfbraun.com` directly. That service's OpenAPI spec (`https://auth.withfbraun.com/openapi.json`) is the authoritative contract and **is actively evolving** — two real discrepancies have already been found between it/its manual and live behavior (an endpoint that didn't exist yet, a response shape that didn't match the docs). Re-fetch and diff against it before trusting any assumption about paths or schemas; don't rely on memory of a previous session's findings.

- `app/services/auth_client.py`'s `AuthClient` (module-level singleton `auth_client`, closed in `main.py`'s `lifespan` alongside the DB `engine`) wraps every call to the auth service: `register`, `login`, `refresh`, `logout`, `get_me`, `update_me`, `get_group_attributes`, `update_group_attributes`, `get_public_key`, `get_group_info`, `get_consent_info`, `grant_consent`, `reject_consent`. **`X-Api-Key` is mandatory on every single method** (`_require_api_key()` raises `RuntimeError` immediately if it's empty, rather than silently sending an empty header — the auth service treats a missing/empty key as "no application context" and skips its consent check entirely, which is a real security-relevant footgun, not just a style choice). `login()` is the one method that returns the raw `httpx.Response` instead of raising on non-2xx: its caller needs to distinguish "200 with tokens" from "403 consent_required" itself.
- `app/security/jwt.py` verifies access tokens locally (RS256) against a public key fetched once from `GET /api/auth/public-key` and cached in a module-level variable guarded by an `asyncio.Lock` — deliberately not `functools.lru_cache` on an `async def`, which would cache the coroutine object rather than its awaited result. Uses **PyJWT**, not the auth service's own manual's suggested `python-jose` (python-jose has a disclosed, unpatched `alg=none` bypass, CVE-2025-61152, and is broadly unmaintained — FastAPI's own docs have moved to PyJWT too).
- `app/api/deps.py`'s `get_current_user` composes JWT verification with the local DB: resolves (or creates, via `INSERT ... ON CONFLICT (auth_sub) DO NOTHING` + re-select — not a naive check-then-insert, which would race two near-simultaneous first requests from the same new user) the `User` row for the verified `sub` claim. `require_admin` builds on it and lets only users with the local `User.is_admin` flag through (403 otherwise) - **this app's administrators are decided by that flag, never by the JWT's `role_name`**: the role belongs to the user across every application on the shared auth service, so an auth-service "admin" would otherwise administer every app. `is_admin` is set directly in the database (default `false`); it is exposed read-only on `GET /api/auth/me` and `GET /api/account/me` and deliberately absent from `AccountUpdate`, so nobody can promote themselves. Feature modules gate their admin endpoints on `require_admin` too (e.g. `event_calendar`).
- `app/api/auth/router.py` exposes `register` / `login` / `refresh` / `logout` / `me` (`GET`) / `update_me` (`PATCH /me`) / `get_group_attributes` + `update_group_attributes` (`GET`/`PATCH /me/group-attributes/{group_id}`) / `group-info` / `consent/{id}/grant` / `consent/{id}/reject`, matching exactly what `frontend/src/context/AuthContext.tsx`, `Account.tsx` and `api/client.ts` call. Non-obvious points:
  - `GET /me`'s upstream response (`MeResponse`) always has `consent_required` + `application_group_id`; `user` is populated only once consent is granted. Our own `/me` converts `consent_required: true` into a 403 with that same `{consent_required, application_group_id}` shape — matching `/login`'s own 403 convention, so the frontend has one code path for both (this also covers entry points that skip `/login`'s check, e.g. Google OAuth). On success, `application_group_id` is merged into the flat response too (`{**user, application_group_id}`), so the frontend can call the group-attributes endpoints below without a second round trip; `PATCH /me` doesn't repeat this merge since that id never changes on a profile edit. `result.get("user") or result` is a defensive fallback for an earlier observed state where a granted response had no wrapper at all — cheap insurance, shouldn't trigger against the currently-published schema.
  - `PATCH /me/group-attributes/{group_id}` **replaces the entire upstream `user_data` object — it is not a partial merge.** Callers (see `Account.tsx` below) must fetch the current value first and send the full merged object. The backend treats `user_data` as a fully opaque JSON blob; the shape it *should* have is defined client-side (`public/config.json`, see below), not here.
  - The auth service's own `UserGroupAttributesPublic` schema documents itself as "user_data only, system_data is hidden" — `system_data` is not reachable through any endpoint this app has credentials for, at any layer, confirmed against the live OpenAPI spec. Don't build backend support for it.
  - Consent is resolved through this template's **own** `/consent` page (`frontend/src/pages/Consent.tsx`), not the auth service's hosted one — it calls `GET /api/auth/group-info` (X-Api-Key only, no user token) to render the scopes, then `POST /api/auth/consent/{id}/grant` or `.../reject`.
- `app/api/account/` is a **separate, local-only** resource (`GET`/`PATCH /api/account/me`) for fields this app owns outright (currently just `nickname`). It depends only on `get_current_user` and the local DB session, and deliberately has **no import of `auth_client` anywhere in the package** — that absence is itself the enforcement that editing local account data can never reach the auth service. When adding real app-specific fields, keep this separation: local data goes through `app/api/account/`, identity/profile data goes through the auth-service-proxying endpoints above.
- Testing patterns specific to this layer (see `tests/conftest.py`): `generate_rsa_keypair()` / `make_access_token(sub=..., **claims)` for signing test JWTs without touching the real service; `respx` mocks every upstream HTTP call (no test should ever hit `auth.withfbraun.com`); route tests that need both a real JWT dependency chain *and* the DB (e.g. `/me`) use `httpx.AsyncClient(transport=ASGITransport(...))` instead of the `client` (`TestClient`) fixture — `TestClient` drives the ASGI app from a separate thread with its own event loop, which conflicts with `db_session`'s connection (bound to the test's own loop); `ASGITransport` keeps everything on one loop. `pytest.ini` also sets a **session-scoped** asyncio event loop for the same underlying reason: `app/database.py`'s `engine` is a module-level singleton whose connection pool can't be split across per-test loops.

### Cross-cutting: backend and frontend version independently
- `backend/version.json` and `frontend/public/version.json` are separate, independently-maintained version markers — there is no shared version number between the two components.
- `GET /api/public/version` reads and returns `backend/version.json` verbatim.
- The frontend's `/version` page (`frontend/src/pages/Version.tsx`) fetches both that endpoint and its own `/version.json`, and flags a mismatch whenever their major.minor versions differ, using the shared `parseMajorMinor`/`compareVersions` helpers in `src/utils/version.ts`.
- `scripts/build.py` packages and tags backend/frontend releases separately (git tags `B-x.y.z` / `F-x.y.z`), so the two genuinely drift independently in normal operation — the `/version` page's compatibility check is the runtime signal for when that drift matters.
- `backend/release_news.json` and `frontend/public/release_news.json` carry the same independence into changelog data: `{unreleased: string[], releases: [{version, release_date, changes}]}`. `GET /api/public/release-news` reads and returns the backend's file verbatim (same pattern as `/version`); the frontend fetches its own `release_news.json` directly, since it's static, in `public/`. The `/release-news` page groups each side's `releases` by major.minor (via the same `src/utils/version.ts` helpers) and renders every generation as a two-column row — a generation with entries on *both* sides gets a "compatible" highlight, one side missing entries reads as an empty column, so (in)compatibility is visible without comparing dates.
- **Every change appends to the relevant `unreleased` array** (see Workflow requirements above). `scripts/build.py`'s `seal_release_news()` moves a component's accumulated `unreleased` entries into a new dated release under the resolved version at STABLE build time, then clears `unreleased` (a no-op, so safe to re-run, if nothing's pending). It edits the local working-tree file, not the git ref being archived — commit the sealed file and create the release tag from that commit *before* running the build, or the archived package won't include the sealed entry.

### Frontend: routing, auth flow, styling
- Routes are declared in `App.tsx` (react-router-dom) and wrapped by `AuthProvider` + `BrowserRouter` in `main.tsx`; page-level chrome (nav bar + language switcher) comes from `components/Layout.tsx`. Pages: `HomePage.tsx` (`/`, public), `Login.tsx` (`/login`, email/password + "Continue with Google"), `Register.tsx` (`/register` — registration alone issues no tokens, per the auth service's own design, so success just shows a confirmation + a link to `/login`, it does not log the user in), `Account.tsx` (`/account`, see below), `OAuthCallback.tsx` (`/oauth/callback` — extracts tokens Google's flow appends as query params), `Consent.tsx` (`/consent`), `ConsentRejected.tsx` (`/consent-rejected`), `Version.tsx` (`/version`, public diagnostic page).
- `Layout.tsx`'s nav bar is the only way to reach `/account` / `/register` / `/login` besides typing the URL directly — it swaps between Login/Register (logged out) and Account/Logout (logged in) links based on `useAuth().user`, plus a CS/EN language switcher (see i18n below).
- `api/client.ts` owns the API base URL (`VITE_API_URL`) and the JWT access/refresh token lifecycle: `apiFetch()` attaches the bearer token and transparently retries once via `/api/auth/refresh` on a 401.
- **Consent redirect is centralized in `AuthContext.tsx`**, not left to callers: both `login()` (on a 403 `consent_required` from `/api/auth/login`) and `loadUser()` (on the same shape from `/api/auth/me`) call an internal `redirectToConsent()` that navigates to `/consent?group=<id>&redirect=<target>`, preserving tokens (the user *is* validly authenticated, just missing consent — don't `clearTokens()` on this path). Four constraints here were all found by live testing against the real service, not by inspection — preserve them when touching this file:
  - `redirectToConsent`'s redirect target falls back to `/` whenever the *current* page is `/login`, `/oauth/callback`, or `/consent` itself, rather than blindly capturing `window.location.pathname`. Consent is very often detected from *within* `login()` itself (not just on page load for an already-protected route), and at that moment the "current page" is always `/login` — capturing it verbatim sends the user back to an empty login form after granting, not anywhere useful.
  - `AuthProvider`'s initial-session-restore effect (the one that calls `loadUser()` on mount if a token already exists) has an **empty dependency array (`[]`), not `[loadUser]`**, and that's intentional. `loadUser`'s identity depends on `navigate` (via `redirectToConsent`), which react-router doesn't guarantee stays referentially stable across navigations; depending on `[loadUser]` let this mount-only check silently re-fire on unrelated route changes, redundantly re-querying `/me` and, if consent was pending, re-triggering the consent redirect using whatever URL it had *just* redirected to as the new target (a doubly-nested `redirect` query param).
  - `Consent.tsx` calls `loadUser()` again right after a successful grant, before navigating away. `AuthContext`'s `user` stays `null` through the entire consent-required window (`loadUser()` returns early without setting it), so without this refresh, navigating to any page that guards on `useAuth().user` (e.g. `Account.tsx`) would immediately bounce back to `/login` on the stale `null`.
  - Both `login()` and `OAuthCallback.tsx` only navigate to `/` when `loadUser()` reports it actually loaded the user (`loadUser()` returns a `boolean`) — navigating unconditionally after a successful token exchange was a real bug (a successful OAuth login would fire `navigate('/')` right after `loadUser()` had already redirected to `/consent`, canceling it).
- Google OAuth needs no backend involvement at all: the browser is redirected straight to `${getAuthUrl()}/auth/google?redirect_uri=...`, the auth service handles the whole exchange with Google, and redirects back to `/oauth/callback` with tokens as query params directly. `VITE_AUTH_URL` is what `getAuthUrl()` reads for this — it's the one place the frontend needs to know the auth service's own public URL, since a browser redirect can't be proxied through the backend like the password-based endpoints are. (`frontend/.env.example` correctly points this at `https://auth.withfbraun.com` and no longer defines an unused `VITE_API_KEY` — both were flagged and fixed in an earlier pass; don't reintroduce either into runtime frontend code. `build.py` does write its own hardcoded `VITE_API_KEY` for a completely separate reason — see Deployment below.)
- Tailwind is v4, CSS-first: there is no `tailwind.config.js`. `src/index.css` just does `@import "tailwindcss"` plus a handful of hand-written base styles, and the `@tailwindcss/vite` plugin (in `vite.config.ts`) handles content detection automatically.
- `CORS_ORIGINS` in `backend/.env.example` (and the `Settings.cors_origins` default) match the frontend dev server's actual default port, `["http://localhost:5173"]` — keep these in sync if either default port ever changes.

### Frontend: internationalization (i18n)
- `react-i18next` + `i18next-browser-languagedetector`, initialized once in `src/i18n/index.ts`. `SUPPORTED_LANGUAGES` (currently `['cs', 'en']`) is the **single source of truth** for which languages ship — `Layout.tsx`'s language switcher iterates over it and `applyUserLanguage()` (below) checks against it; don't hardcode a separate language list anywhere else. Detection order is `localStorage` before `navigator`, with `cs` as `fallbackLng` (this template originates from a Czech-first product) — `supportedLngs` must stay pinned to the same list `resources` actually ships, or an unrecognized locale resolves to a partial/missing bundle.
- Translation keys are namespaced per page in `src/i18n/locales/{cs,en}.json` (`login.*`, `account.*`, `common.*` for shared strings, etc.) — every page component calls `useTranslation()` and reads its own strings via `t('page.key')`; there's no untranslated hardcoded copy anywhere in `src/pages/`.
- `applyUserLanguage(languageCode)` (exported from `src/i18n/index.ts`) is a fallback **cascade**, not a straight assignment: the signed-in user's own `language_code` if this app ships that language, else `'en'` if that's shipped, else **leave the current language untouched** (whatever was active before — a manual switcher choice or the detector's result). It's called from `AuthContext.tsx`'s `loadUser()` (covering session restore, login, and Google OAuth — every path that resolves who the user is) and again from `Account.tsx` after saving the Profile card, so editing `language_code` there takes effect immediately without a reload.

### Frontend: theming (light/dark mode)
- Dark mode is **class-based, not OS-preference-based**: `src/index.css` declares `@custom-variant dark (&:where(.dark, .dark *));` (Tailwind v4's CSS-first equivalent of `darkMode: 'class'`), so every `dark:` utility across the app activates only when a `.dark` class is present on `<html>` — it deliberately does not follow the OS's `prefers-color-scheme`.
- `src/context/ThemeContext.tsx`'s `ThemeProvider`/`useTheme()` owns two pieces of state: `darkMode` (the active local theme — defaulting to `false`/light, toggling the `.dark` class on `document.documentElement` and persisting to `localStorage`'s `dark_mode` key in a `useEffect`) and `profileDarkMode` (the last known value of the signed-in user's **profile-stored** preference, `boolean | null` — `null` until it's been fetched or set at least once). Both live in context, not in any one page's local state, specifically so every consumer — either `ThemeToggle` instance, the Account page's stored-value display, and its save payload — reads and writes the same shared value regardless of which one triggered a change. This provider works standalone for a logged-out visitor (`profileDarkMode` just stays `null`) — populating it for a signed-in user is layered on top in `AuthContext.tsx` and `Account.tsx`, not inside `ThemeContext` itself.
- `main.tsx` nests `<ThemeProvider><AuthProvider><App /></AuthProvider></ThemeProvider>` — **that order matters**: `AuthContext.tsx`'s `loadUser()` calls `useTheme()` to apply the server-stored preference once the user resolves, so `ThemeProvider` must already be an ancestor.
- The stored preference lives at `user_data.darkMode` (`true`/`false`) via the existing group-attributes endpoints — **not `system_data`**, even though the field is conceptually closer to an app setting than user profile data. `system_data` is confirmed inaccessible to this app's credentials (see Authorization above); this was a deliberate scope decision, not an oversight, when this feature was built.
- `src/theme.ts`'s `persistDarkModePreference(groupId, darkMode)` is the write path: fetch the current group-attributes, merge `darkMode` into the existing `user_data` (PATCH replaces the whole object, same constraint as the config.json attributes below), then PATCH. It's best-effort and swallows errors — the local theme (already applied via `ThemeContext`) doesn't depend on the server save succeeding.
- `src/components/ThemeToggle.tsx` is one shared toggle switch, rendered in both `Layout.tsx`'s header nav and `Account.tsx`'s dedicated theme section, so the two controls behave identically: on click it flips the local theme immediately via `setDarkMode`, and — only when signed in (`user?.application_group_id` is set) — fires `persistDarkModePreference` *and* `setProfileDarkMode(next)` in the same click, optimistically (not awaiting the PATCH), with no separate save step. Because `setProfileDarkMode` writes to `ThemeContext` rather than a component-local callback, it doesn't matter which instance of `ThemeToggle` is clicked — both the header's and the Account page's stay in sync immediately. The thumb's own positioning deliberately avoids `position: absolute` with no explicit `left`/`right` (that renders on the wrong side, since the browser falls back to an ambiguous "static position") — it uses `inline-flex items-center` on the track and `inline-flex items-center justify-center` + `translate-x-*` on the thumb instead, which positions deterministically; the latter also centers the sun/moon glyph the thumb renders for the active mode.
- `AuthContext.tsx`'s `loadUser()` best-effort fetches group-attributes after resolving the user and calls both `setProfileDarkMode(stored)` (`stored` defaulting to `false` when unset) and, **only if the field is an explicit boolean**, `setDarkMode(data.user_data.darkMode)` — an unset preference (new user, or a config predating this feature) leaves the *active* theme untouched (whatever was already active — localStorage value or a pre-login manual toggle) rather than forcing a reset to `false`, while still seeding `profileDarkMode` so the Account page's display is correct from the start.
- `Account.tsx` renders a third, visually separate block below the two `<form>` cards (a plain `<div>`, not inside the Profile `<form>` — it has no Save button of its own since `ThemeToggle` already saves on click): it shows `storedDarkMode` (read straight from `ThemeContext`'s `profileDarkMode`, defaulting to `false`) labeled as "stored in profile", contrasted against the currently-active `darkMode` from `useTheme()`, surfacing a divergence warning whenever they differ. Because both values come from the same shared context, this only fires for a *genuine* mismatch (e.g. a stale `localStorage` value from a previous session, not yet reconciled) — not merely because some other component's toggle click hasn't been reflected here yet. Its own group-attributes fetch (on mount) seeds `profileDarkMode` via `setProfileDarkMode`, and a separate `useEffect` mirrors `profileDarkMode` back into `attributeValues.darkMode` (the state object the Profile card's Save button PATCHes) whenever it changes, so a plain Save click never PATCHes back a stale value even if the theme was toggled from the header since the page loaded.

### Frontend: configurable auth.user attributes (`public/config.json`)
- `public/config.json` declares extra, app-specific fields to render on top of auth.user's core profile fields on the Account page's Profile card — each entry has a `key`, a `bucket` (`user_data` or `system_data`), a `type` (`text` / `number` / `boolean` / `date`), a `required` flag, and an `i18nKey`. It's fetched at runtime via `loadUserAttributes()` in `src/config/userAttributes.ts` (it's static, in `public/`, not a build-time import — editing it doesn't require a rebuild).
- **Only `bucket: "user_data"` entries ever render or save.** `system_data` entries are dropped by `loadUserAttributes()` with a `console.warn`, not silently ignored — this app's credentials can never read or write `system_data` on the auth service (see Authorization above), so a `system_data` config entry would otherwise look like a real field that silently fails to save. A config file may still declare `system_data` entries for documentation purposes; don't build a code path that tries to render one.
- `DynamicAttributeField.tsx` renders one control per attribute based on `type`. Saved values round-trip through `PATCH /api/auth/me/group-attributes/{group_id}` — since that endpoint replaces the whole `user_data` object (see Authorization above), `Account.tsx` always sends the full known set of attribute values on save, not just whichever one changed.
- `Account.tsx`'s two cards never cross endpoints: the Account card (`nickname`) only ever calls `/api/account/me`; the Profile card (core fields + the config-driven attributes above) only ever calls `/api/auth/me` and its group-attributes endpoint. Each card has its own independent saving/error state so one failing never blocks the other. One nuance worth preserving: controlled inputs store an unset field as `''` (React inputs can't hold `null`), but the auth service validates fields like `birth_date` as a real date-or-absent and rejects `""` outright — `Account.tsx`'s `blankToNull()` converts blanks to `null` right before the `PATCH /api/auth/me` request.

### Feature modules (pluggable, per-application)
This template ships the **structure** for optional feature modules (e.g. an administration area, reservations, orders) that can be pre-built once, then turned on/off and customized per application — it ships **no concrete modules of its own**. Both sides follow the same shape: a module is a self-contained package under a conventional folder, auto-discovered without editing any shared wiring file, and gated by its own enable-list.

- **Backend** (`app/modules/<key>/`): a subpackage whose `__init__.py` exposes `manifest = ModuleManifest(key=..., router=..., ...)` (`app/modules/base.py`). `app/modules/registry.py`'s `discover_modules()` walks every subpackage of `app.modules` via `pkgutil` and imports it; a subpackage with no `manifest`, or whose `manifest.key` doesn't match its folder name, is skipped with a `logger.warning` rather than crashing the app. `load_enabled_module_keys()` reads the `enabled` array of keys from **`backend/modules.json`** — git-tracked, same `{"enabled": [...]}` shape as the frontend's `public/modules.json` — and `get_enabled_modules(keys)` filters discovery down to it; `app/api/router.py` loops over that and mounts each enabled module's router under `/api/modules/<key>` (or `manifest.prefix`, if set). **Enabling/disabling a module never touches the DB schema** — `import_all_module_models()` is called once from `alembic/env.py` and imports `<module>.models` for *every discovered* module regardless of enabled state, so migrations stay identical across deployments no matter which modules a given application has turned on; enabled/disabled only gates whether a module's router gets mounted. This is what lets a module be dropped into `app/modules/` and picked up everywhere (routing, migrations) without hand-editing `router.py` or `alembic/env.py` again. The module selection deliberately does **not** live in `Settings`/`.env` (it used to be `ENABLED_MODULES` there, now ignored): `.env` is untracked and shared by every branch checked out in the same working tree, so switching to another application branch silently kept the previous one's modules. A missing `modules.json` means no modules; a malformed `enabled` value raises at startup; and `tests/test_modules_registry.py` fails the suite if the branch's committed file enables a key that no discovered module has.
- **Frontend** (`src/modules/<key>/index.tsx`): default-exports a `ModuleDefinition` (`src/modules/types.ts`) — `key` (must match the folder name and an entry in `public/modules.json`'s `enabled` array), `routes` (`{path, element}[]`, same shape as react-router-dom's `<Route>`), optional `nav` (`{to, labelKey}[]`), optional `footerLinks` (same shape, rendered as a link row in `components/Footer.tsx`, which calls `useEnabledModules()` itself rather than receiving modules from `Layout`), optional `headerWidget`, optional `locales` (per-language translation objects). `src/modules/registry.ts` uses Vite's `import.meta.glob('./*/index.tsx', { eager: true })` to import every module at startup with no per-module import statement anywhere else, registers each one's `locales` as its own i18next namespace (`i18n.addResourceBundle(lang, key, ...)`) **unconditionally** — same rationale as the backend always registering models: cheap, and keeps enable/disable a pure routing/nav concern — and exposes `useEnabledModules()`, a hook that fetches `public/modules.json` once (cached) and returns only the enabled subset. `App.tsx` spreads `module.routes` into `<Routes>` and `Layout.tsx`'s `Nav` spreads `module.nav` into the header, both driven by that hook — neither needs to change when a module is added, removed, or toggled. A nav item's `labelKey` must be namespaced as `"<moduleKey>:<key>"` (i18next's default `nsSeparator`) to resolve against that module's own bundle rather than the core `translation` namespace.
- **`backend/modules.json` and `frontend/public/modules.json` are independent config files, kept in sync manually per branch** — each application branch commits its own selection in both, `core` ships both as `[]`. Same independence as the rest of backend/frontend config in this template (see "Cross-cutting" above). There's no runtime cross-check; enabling a module on one side but not the other will produce a UI with no backend to call, or API routes with no frontend entry point.
- **A module's own non-secret settings (texts, switches) go in a git-tracked `backend/modules/<key>.json`**, loaded and validated by the module itself — for the same per-branch reason as `modules.json`. Secrets and per-server values (SMTP, `CONTACT_MAIL`, Stripe keys) stay in `.env`. `kontaktni_formular.json`: `send_reply`, `default_language`, and `reply_templates.<lang>.{subject,body}` for the sender's confirmation email. The template is picked from the request's `language` (the frontend sends `i18n.resolvedLanguage`): exact match first, then the primary subtag, else `default_language`. Placeholders are limited to `{sender_name}`, `{reply_to}`, `{subject}`, `{message}`, and all of it is validated on load (`app/modules/kontaktni_formular/config.py`), with a test guarding each branch's committed file. `event_calendar.json` holds `page_size` (editors are the app's `is_admin` users, see `require_admin` above); its uploaded images go under `Settings.uploads_dir`/`event_calendar/` (`UPLOADS_DIR` in `.env`, a per-server path) and are served by the module's own `GET /uploads/{filename}`.
- A real module is free to diverge from this contract in its own app-specific ways once created (extra files, its own sub-router structure, etc.) — the only hard requirements are the `manifest`/`ModuleDefinition` shape discovery depends on and the `key` match. Building actual modules (administration, reservations, orders, ...) belongs on `core` if they're broadly reusable, or directly on an application branch if they're one-off.

Every hand-written source file (backend `.py` under `app/`, `tests/`, `alembic/`; frontend `.ts`/`.tsx`/`.css`) starts with the project header — a `#`-comment block in Python, a `/** ... */` block in TS/TSX/CSS:
```
Part of the With FBraun project template.
Author: František Braun <frantisek.braun95@gmail.com>
```

It goes as the very first lines of the file — after a shebang if one exists, or before a `.d.ts` file's triple-slash reference directive, or above (never inside) an Alembic migration's auto-generated revision docstring, since Alembic's own tooling reads that docstring verbatim. Add it to new files as you create them.

### Deployment (`scripts/`)
- `build.py` archives `backend/` / `frontend/` / `scripts/` from a git ref (a `B-`/`F-` tag in STABLE mode, `HEAD` in SNAPSHOT mode), builds the frontend with `npm install && npm run build`, and uploads the resulting zip to FTP per `scripts/build.config.toml` (gitignored; copy from `.example`). For STABLE backend/frontend builds it first seals that component's `release_news.json` under the resolved version (see Cross-cutting above) — commit the sealed file and create the release tag from that commit before running the build, or the archive won't include it.
- `build_frontend()` writes its own build-time `frontend/.env` with a **deliberately public, shared trial `VITE_API_KEY`**, read from `build.config.toml`'s `client_api_key` (gitignored, like the rest of that file). It exists purely so people can try the packaged template's own live demo build without first registering their own application on the auth service. **This is not a pattern to copy for a real application** — a real app must never send its API key from the browser at all (see the BFF note under Authorization above); this key only exists because the template's own demo build has no backend-held key of its own to proxy through. Don't add a real app's `VITE_API_KEY` here, in `.env.example`, or anywhere else client-side.
- `install.sh` / `upgrade.sh` are Linux-only systemd + nginx deployment scripts (require `psql`, `nginx`, `systemctl` on `PATH`) driven by `scripts/deploy.config.sh` (gitignored; copy from `.example`). They provision the Postgres role/DB from `backend/.env`'s `DATABASE_URL`, and health-check via `GET /api/public/version` after `upgrade.sh` restarts the service — a change that breaks that endpoint will trigger `upgrade.sh`'s automatic rollback. `build_scripts()` bundles these together with the current, real `backend/.env` — unlike the backend/frontend archives (built from a git ref), this bundle always reflects the current local filesystem and is never meant to be redistributed as part of the template, only pushed to this project's own live server.

## Application: BumpFeel

**Name:** renamed from ThoughtAuction (Czech "Aukce myšlenek") on 2026-10-26. The name is shown in `nav.brand` and `home.title` of both locale files, `index.html`, `legal.json`, the FastAPI title, the email subjects (`kontaktni_formular.json`, `boards/documents.py`) and the Stripe description (`boards/payments.py`). **Deliberately not renamed:** the database `thoughtauction_db` (`config.py`, `.env.example`; a deployment's database is the owner's business), the git branch `thoughtauction` (it is what the "Branches synced from `core`" list below and the `new-module` skill name, and the Alembic merge revisions refer to it as "merge ... into thoughtauction"), and `.claude/` notes that mention the branch. So a search for the old name that finds only those is expected.

**Purpose:** A website with several publication boards (categories) where anyone can post their own contribution and pay to push it higher up the board.

**Boards and posts**

- The core of the app is a simple, clear, infinitely scrolling page of user posts, ordered by their current value (highest first). There are several boards (categories); each one is its own such page.
- A post has only a **title and a text of at most 2048 characters including spaces**. **No author is shown**, only the title, the text and the post's current value.
- **Post value** = paid amount (1 USD = 10 points) + resonances (1 user's agreement = 1 point) - age (1 day = 1 point), **and never below 0** (since 2026-10-15, at the author's request: an old post nobody paid for or resonated with shows 0, not a negative number - and the floor applies to the process too: the next resonance or payment on such a post shows in full, so one resonance on an old post makes it 1).
- Posting and expressing resonance are **for signed-in users only**; **creating a category is for administrators only** (since 2026-10-19, at the author's request: ordinary users only add posts, to any category). Reading is public.
- **Resonance**: a user can give one resonance to a given post only once. Nobody sees who resonated - not even the post's author - only the count.
- A post's author can **pay for it repeatedly**; payments accumulate, so each new payment raises the value by the amount paid.
- Appearance: the original brief was deliberately plain (no colors, just a bold title and the message). **Since 2026-10-13, at the author's request, a board looks like a contest for placement** - separate cards, rank badges, a podium for the first three, a violet action colour - see "The look" below. The posts themselves are still only a title and a text with no author, and the post form is still text only, with emoji support.
- A **category** has a title (the slug is generated from the title; on a collision a sequence number is appended) and a short description of at most 4096 characters including spaces.
- When a category is created, a **machine evaluation (machine rules) of the category** is produced - algorithmically first and later also by an AI model - used afterwards to compare whether a post matches the category's intent. An administrator can view and edit these machine rules.
- System pages: **Terms** (rules and conditions), **GDPR** and **Contact**.

**Moderation**

- An administrator can mark a post as violating the public rules and delete it with **no refund** of the payment. If a user has more violating posts within a given period (stated in the rules and controlled by a parameter), the **account is blocked and all of the user's posts are removed without compensation**.
- Violation checking has three levels:
  1. **Algorithmic** (local) - evaluates a post, and a category's title and description, *before publication and before the payment is confirmed*. If it does not meet the rules, the user gets a message that publication is not allowed.
  2. **AI model via API** - the content is sent to an AI model to be judged against the rules. **Not in the first development version**: only the preparation for the call is built, as a **mock**, with no real model connected yet.
  3. **Manual, by an administrator** - can find any post and block it with a stated reason, which is sent to the author and shown as an in-app notification.
- The local algorithm returns a **violation score in %**: above 30 % the user is shown a notice that they should edit the post; above 50 % the content is shown as potentially violating and may be blocked without refund on closer review; above 75 % it is violating and publication is not allowed.
- It also checks **whether the post matches the topic of its category** (against the category's machine rules). The same thresholds apply to the mismatch score: above 30 % an edit is recommended, above 50 % potential risk, above 75 % not allowed.
- When a category or post is judged violating, the author is shown a message with the reason and the specific aspects behind it.
- In scope for the first version: the local algorithms for posts and categories, and the AI-call preparation as a mock only.

**Implemented so far - the `boards` module: boards, posts, resonance, moderation and payments**

- Backend `app/modules/boards/` and frontend `src/modules/boards/`, enabled in both `modules.json` files; its settings (`page_size`, points per USD / resonance / day of age) live in `backend/modules/boards.json`. UI and routes call boards *categories* (`/categories`, `/categories/:slug`, `/categories/new`); the slug comes from the title (`slugify`/`unique_slug` in `service.py`, `-2`, `-3` ... on a collision, `new` is reserved).
- **Who creates categories** (`deps.get_active_admin`): `POST /categories` and `POST /categories/check` need an administrator - the local `User.is_admin` flag, never the auth service's role - whose account is not blocked; anyone else signed in gets 403 `{"code": "admin_required"}`, a blocked account is told `account_blocked` first, and an anonymous caller gets 401. Ordinary users only *post* into categories (any of them) - `POST .../posts` is open to every active user. The frontend follows the same rule: `CategoriesList` shows "New category" only when `useBoardsMe().is_admin`, and `/categories/new` shows the form to an administrator, an explanation to a signed-in user who is not one, and the sign-in link to a visitor (an administrator may be signed out). Categories that users made before this rule are untouched - their `created_by_id` stays, so their creators are still notified when an administrator blocks or restores them. An administrator's category goes through the same content check (`enforce`) and gets machine rules like any other. Tests that need a category through the API create it as an administrator (the `admin` fixture); seeding one straight into the database needs no one.
- **A post's value is computed on read** (`service.post_value`) and never stored. The listing orders by `service.rank_expression` instead - paid points + resonance points + `points_per_day` x created-time-in-days - which gives the same order as the value at any moment (the `now` term is the same for every post and cancels out), so page boundaries stay stable between loads. Posts with equal shown values come in arbitrary but stable order. Don't "simplify" it into a per-row age computation in SQL. **The shown value is floored at 0, and so is the process**: `post_value` returns `max(0, points + floor_lift - age)`. A bare `max(0, ...)` would be a trap - an old post's credits would first pay off the age it had already "lost" below zero, so a resonance (or a payment) on it would change nothing visible. `Post.floor_lift` prevents that: every credit's UPDATE (`router.add_resonance`, `payments.apply_boost`) adds `service.lift_for_credit(config, now)` - the post's shortfall below zero, measured against the row *as it was before the credit* (an UPDATE's right-hand sides all see the old row, so it is one atomic statement, and two simultaneous credits each get theirs) - and only then the credit, so the post starts from exactly 0 and the credit shows in full. **Only a credit ever changes `floor_lift`, never the clock**, so the value is still a pure function of the row and the time, and the ordering key `rank_expression` (= points + `floor_lift` + `points_per_day` x created-days) stays time-invariant - the floor never reverses an order, it only makes more posts equal, and the key is deliberately *not* floored so posts that all show 0 stay ordered by what they have actually earned. The lift is *not* a pause: a lifted post goes on ageing from where it was lifted. Consequences to remember: the lift is computed with the factors in force *when the credit arrives*, so changing `points_per_day` later does not rewrite past lifts; posts created before the column existed have `floor_lift` 0, which is exactly how they were shown under the plain floor; and code that adds points to a post any other way (a new credit type) must add `lift_for_credit` to the same UPDATE or that credit will be eaten again.
- `Post.paid_cents` (the running total paid for a post, in cents) feeds the value formula; **only a confirmed payment writes it** (see Payments below), and the `stripe_payments` table of the gateway module is the ledger.
- **The look** (`boards/styles.ts`, light and dark): a post is a card (`PostCard.tsx`) in a leaderboard (`PostList.tsx`, titled "Žebříček"). Its place is its position in the list (`rank = index + 1`, ties keep the list's stable order - they are not shared places), shown as 🥇🥈🥉 for the first three, whose cards get a gold / silver / bronze tint, and as `#4`, `#5` ... below; the value is the big score on the right. After a refresh a card says how many places it climbed or lost (`▲ 3` / `▼ 1`) **counted only among posts that were already on the board** (`movesBetween`): a new post at the top pushes everybody down without anyone losing a place to it, but a post that overtook ten others is `▲ 10` and each of those is `▼ 1`. The chips last until the next refresh. `styles.ts` holds the shared classes - violet is the action colour (`primaryButton`, `secondaryButton`, `chip`), gold / silver / bronze belong to the podium and the payments total only, emerald / amber / rose label states - so a new page should use them rather than invent its own. Rules found while checking it: a podium tier's `card` class is the *whole* card look (it must not be stacked on the plain `card`: two `border-*` colours on one element are resolved by stylesheet order, not class order); dark-mode buttons use `violet-600`, because white on `violet-500` is under 4.5:1; and state colours must not carry the meaning alone (every chip has text). Transitions do not run while the Browser pane is hidden, so computed colours read mid-change - switch them off (`* { transition: none !important }`) before measuring. The category page opens with a banner, the category list is a grid of tiles, and My posts / My payments / My receipts are cards.
- **The board refreshes itself** (`PostList.tsx`): because other readers' resonances and payments move posts, the list fetches itself again - **as many posts as the reader has loaded, page by page, replacing what is shown** - every 60 s while the tab is visible, when a tab that was in the background comes back, and right after the reader's own resonance (`PostCard` reports it through `onChange`). Rules worth keeping when touching it: loading the next page and refreshing share one `busy` flag (a refresh asked for meanwhile is queued, never dropped); every refresh, whoever started it, restarts the 60 s timer (a setTimeout chain, not an interval - the timer is a fresh `setTimeout` armed at the end of each refresh); a refresh is silent on failure and keeps the list as it was; it always fetches at least the first page, so an empty board picks up its first post; and it bumps `revision` so the scroll observer looks again, because a sentinel that stays in view fires no second event and a load skipped while busy would otherwise leave the reader stuck at the bottom. Fetching N loaded posts costs N/`page_size` requests per minute per open tab.
- **Authors are never exposed**: `Post.author_id` / `Category.created_by_id` are stored for moderation only, `PostOut` / `CategoryOut` omit them, and who resonated is only ever a row in `module_boards_resonances` (composite primary key = once per user and post; `resonance_count` is denormalized and moved in the same transaction). A viewer sees only their own `resonated_by_me`. The public listing uses the module's `get_optional_user`, which treats an invalid or expired token as anonymous - the frontend sends its stored token on every request, so a 401 there would log a visitor out of a page that needs no login.
- Text limits are fixed constants, not config (changing one needs a migration): post title 120 (our choice - the spec gave none), post text 2048, category title 120, description 4096. They count characters (code points), so an emoji is one; the frontend mirrors them in `boards/api.ts` (`charCount`) and its textareas deliberately have no `maxLength` (it counts UTF-16 units).
- **Moderation** (`app/modules/boards/moderation/`, `admin_router.py` under `/manage`, UI at `/moderation`), three levels:
  1. *Local* - `scorer.py` (violation score in percent from a small cs/en `lexicon.py` plus shape heuristics, each aspect a probability combined as independent signals, seeing through spaced-out letters / digits / stretched letters) and `topic.py` (mismatch against the category's **machine rules** - keywords built from its title and description, stored in `Category.machine_rules`, editable by administrators). A percent must be strictly *above* `warn_percent` / `risk_percent` / `block_percent` (30 / 50 / 75, `ModerationConfig` in `boards.json`) for the level "warn" / "risk" / "blocked". The topic score is deliberately **damped by confidence** (distinct words in the post, keywords in the rules): lexical matching is weak evidence, so a short post or a sparsely described category can at most advise, never hard-block - tune `topic_*` in `boards.json` before loosening it.
  2. *AI model* (`ai.py`) - **prepared, not connected**: request, prompt, response schema and a validating parser exist, only `MockAiModerator` is wired in (`get_ai_moderator()` is the one place to swap it, and `ai_review_enabled` is off). Any failure of the AI call is ignored - the local checks have already run.
  3. *Manual* - an administrator (`User.is_admin`, never the auth role) blocks a post with a reason: `status="blocked"`, removed without refund (`paid_cents` is left untouched - there is no refund path), the author gets a notification through the `notifications` module (i18n keys `boards:notification.*`, in this module's own locale bundle).
- **The gate**: every new post or category is assessed first (`router.enforce`) - 422 `moderation_blocked` above the block threshold, 409 `confirmation_required` at risk level unless the request has `confirm_risk: true` - and `POST .../check` returns the same verdict without writing anything, which is what the frontend shows before publishing. The scores and findings are stored with the post (`Post.assessment`) for the administrator. When payments are built, this check must run **before a payment is confirmed**.
- **Strikes**: a blocked post counts as a strike; `strike_limit` of them within `strike_period_days` (3 / 30 in `boards.json` - state the same numbers in the public rules) block the account (`User.is_blocked`) and take its remaining published posts down as `removed` - which are not strikes themselves. A blocked account fails every write with 403 `account_blocked` (`deps.get_active_user`) but can still read; the frontend learns it from `GET /me` (`useBoardsMe`). Unblocking sets `User.strikes_reset_at`, so earlier violations stop counting. Only `published` posts are public: listings, counts and resonating all filter on it.
- **Hiding a post** (`Post.status` `hidden`; `POST /me/posts/{id}/hide` and `.../show`, both on the signed-in user's own post; buttons on the author's card on the board and on `/my-posts`): the author takes a post off the boards and may show it again. It is **only a state** - `paid_cents`, resonances and `created_at` are untouched, nobody is refunded, and **the value keeps falling with age while it is hidden** (it is computed from `created_at`, so there is nothing to freeze or to reset; a test pins that showing a post does not make it young again, and don't "fix" it). Everything that filters on `published` (listings, counts, resonating, `resolve_boost`) therefore already leaves a hidden post out; `resolve_boost` says "hidden - show it first" instead of "no longer published". Rules: hide / show are idempotent, an other user's post is a plain 404, a blocked account gets 403 `account_blocked` (`get_active_user`), a `blocked` or `removed` post is 409 for both - only an administrator undoes those. **Hiding is not a way out of moderation**: an administrator can still block a hidden post (a strike like any other; 409 `Post is not published` only for blocked / removed), `enforcement.block_account` takes hidden posts down with the account (otherwise the author could show them again after an unblock), and the administrators' restore refuses a hidden post (it is the author's doing, not a block). The administrators' post list has a `hidden` state filter. The label "hidden" on `/my-posts` means the author hid it; a published post whose category is blocked is `categoryBlocked` there (and in the payment overview's `postState`) - keep the two apart.
- **Restoring a post** (`POST /manage/posts/{id}/restore`, `enforcement.restore_post`): a `blocked` - or `removed` - post is published again, its author notified (`boards:notification.postRestored`), and since it is no longer `blocked` it stops being a strike, so withdrawing a mistaken block also keeps the author's account clear of the limit. It keeps `paid_cents`, resonances and its age (the time it was down is not made up for). **Refused with 409 `author_blocked` while the author's account is blocked** - unblock first, then restore: a published post of a blocked account would contradict the block, and unblocking deliberately restores nothing by itself (the posts taken down with an account are restored one by one, status filter `removed` in the UI). The moderation fields are cleared on restore and there is no audit log of moderation actions - the notification rows are the only trace.
- **Blocking a category** (`Category.status` `published`/`blocked`, `moderation_reason`, `moderated_at`, `moderated_by_id`; `POST /manage/categories/{slug}/block` with a reason and `.../restore`, `GET /manage/categories` lists every category with filters; the Categories tab of `/moderation`): the board **disappears for visitors but nothing in it is touched** - its posts keep their own state, `paid_cents` and resonances, nobody gets a strike (the posts' authors did nothing wrong, and the spec's strikes are about posts), and restoring it undoes everything. Its creator is notified of both (`boards:notification.categoryBlocked` with the reason, `categoryRestored` with a link); the posts' authors are not written to - they see their post as *hidden* on `/my-posts` (`MyPostOut.category_blocked`) without the reason, which is the creator's business. Hiding works through one rule - `views.get_category(db, slug, include_blocked=False)` makes a blocked category a 404 for the listing, the board, its posts, the draft check and posting - plus the three places that reach a post without going through its category: the public category list, resonating (`router.add_resonance` joins the category) and `payments.resolve_boost` (409 "The category is blocked"); a new place that looks a post up by id must do the same. The administrators' rules endpoints pass `include_blocked=True`. The slug stays taken (the unique index), so nobody can re-create the title and slip past the block. A payment that was already in flight when a category was blocked is still recorded on its post - the money has been taken.
- **Payment overview** (`history.py`, `GET /me/payments`, the `/my-payments` page): every `post_boost` payment the user started, newest first, whatever became of it - `pending`, `paid`, `failed`, `expired` - with the post's title and state *today*, `category_blocked`, and the document issued (`receipt_id` / `receipt_number`; the page links to `/receipts?receipt=<id>`, which opens that document, falling back to the newest). The summary (`paid_count`, `paid_cents`) covers **completed payments only, in USD, over every page** - an abandoned checkout is not money spent. The payments table belongs to the gateway and knows nothing of posts, so `history.entries` ties a payment to its post through `reference` (the post's id) in Python and one `IN` query rather than a joined cast, which would keep the posts' index from being used. Nothing is refunded for a blocked post and the page says so; there are no refund rows because the gateway records none.
- **Terms, GDPR, Contact**: the pages are the existing modules switched on, not new code. Terms ("Pravidla a podmínky", `/obchodni-podminky`), Privacy (`/ochrana-osobnich-udaju`), About and Cookies are `stripe_payment_gate`'s legal pages - the same module that takes the payments, enabled on both sides - and Contact (`/contact`; the old `/kontakt` redirects there) is `kontaktni_formular` on both sides (`CONTACT_MAIL` per server in `.env`, reply texts in `backend/modules/kontaktni_formular.json`). The Terms and Privacy texts in `legalLocales.ts` are rewritten for BumpFeel (content rules, the checks and thresholds, strikes, anonymous authors, the value formula, no refund for a blocked post, Art. 22 GDPR wording for the automatic account block) - a divergence from the template's e-shop texts, so expect a merge conflict there whenever `core` touches that file. The numbers the texts quote come from `public/legal.json`'s `params` (a small generic addition to `legal.ts`), and `tests/test_modules_boards_legal.py` fails if they stop matching `boards.json` / the models - change a threshold, the strike rule, a limit or a point factor and update `params` and the effective date together.
- **Before going live**: fill `provider` (name, IČO, address, email) and `effectiveFrom` in `legal.json` (the pages show a warning banner until then); have a lawyer read the Terms and Privacy - they are drafts, in particular the no-refund clause, the 14-day withdrawal / immediate-performance wording, the licence to display content, the identity-disclosure rule and the retention periods; when the AI moderator is connected, update Terms (the checks) and Privacy (a new recipient, a transfer, the automated-decision wording); work through the checklist in the `stripe_payment_gate` README (Stripe activation needs the legal pages filled in, the webhook endpoint, VAT / OSS and the electronic tax document, which this application does not issue) and put the live `STRIPE_*` keys and the right `FRONTEND_URL` on the server.
- **Payments** (`app/modules/boards/payments.py`): an author pays a whole number of USD (`payments.min_amount_usd` / `max_amount_usd` in `boards.json`, 1-500) to raise their *own, published* post. It is the `post_boost` purpose of `stripe_payment_gate` (Stripe Checkout; needs `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and a `FRONTEND_URL` that is the frontend's real address - `.env.example` says port 3000, Vite serves 5173). `resolve_boost` validates everything the payer chose: the amount (a real whole number in range, not a boolean or float), that the post is theirs (someone else's is a plain 404, indistinguishable from a missing one), still published, account not blocked. `apply_boost` runs exactly once per payment, in the confirming transaction, and adds to `Post.paid_cents` with one atomic UPDATE, so payments accumulate. The purpose uses a small generic addition to the gateway, `PaymentPurpose.required_consents`, to make the `terms` and `digital_content_waiver` consents (the express request for immediate performance that ends the 14-day withdrawal right) non-bypassable on the server. Nothing is refunded, and a payment that lands after a post was blocked is still recorded - the money has been taken. The frontend asks `GET /payments` whether payments are on (gateway in `modules.json` *and* both keys set) and hides the option otherwise; an author finds their anonymous posts through `PostOut.mine` (true only for the viewer's own post, with `paid_cents` then filled in) and `/my-posts`. To click it through locally, point `STRIPE_API_URL` at a stand-in that implements `POST /v1/checkout/sessions`, `GET /v1/checkout/sessions/{id}` and sends a signed webhook - the tests mock Stripe with respx instead.
- **Paying with a new post** (`PostForm.tsx`, `PostBoostFields.tsx`; frontend only - it chains the existing endpoints, no backend change): where `GET /payments` says payments are on, the new-post form takes an optional amount in whole USD (`parseBoost`: empty = nothing, a whole number in range = pay, anything else blocks the submit). Order of events on submit: the content check (`/posts/check`, or the review panel's "publish anyway and pay"), then `POST .../posts`, then `startCheckout(POST_BOOST, ...)` with the consents `terms` and `digital_content_waiver` - so **the content check always precedes the payment** and `resolve_boost` still validates the post and the amount like for any boost. **Publishing does not depend on the payment**: Stripe being unreachable, or the payer cancelling at the gateway, leaves a published post with `paid_cents` 0 (the gateway leaves a cancelled payment `pending` until Stripe reports it expired), and when the checkout cannot be started the form says so and `onPosted` brings up the usual offer to raise the value. A post that only goes live once paid would be a different design (a pending state, a draft lifecycle) - it was not chosen. The form is `busy` for as long as the redirect takes: `startCheckout` never resolves on success. The consent checkbox and the gateway's terms notice (`stripe_payment_gate:button.termsNotice`, shown in place of the plain rules notice) sit next to the submit button because the consent is only valid if the terms were presented next to the control that starts the payment - the gateway's own `PayButton` does the same for a boost on an existing post.
- **Payment documents and the confirmation email** (`documents.py`, `receipts.py`, `GET /me/receipts`, the `/receipts` page): every confirmed payment gets a numbered document, created in `apply_boost` - the same transaction that raises the value - so a payment never exists without it and a rolled-back one never leaves a number behind (`2026-000001`, one `INSERT ... ON CONFLICT DO UPDATE` on `module_boards_receipt_counters`, gapless within a year of the provider's time zone). It is stored as an immutable **snapshot** (`Receipt.document`: issuer, payer's email, post title, amount) and rendered from that, never from live data. The email goes out in the gateway's `after_paid` hook, i.e. only once the payment is committed; the outcome is on the receipt (`emailed_at`, `email_attempts`, `email_error`), a failure never touches the payment, and failed sends are retried with the next confirmed payment and by an administrator (`POST /manage/receipts/retry`) - there is no scheduler, so if nothing is paid a failed email waits for that call (the payer can always read the document in the app). The payer's email comes from the sign-in token and is kept in `payment.extra` by the gateway; a payer without one still gets a document, in the app only. The document is HTML - the email body and the sandboxed frame on `/receipts` show the very same markup, with every outside value escaped - not a PDF (no PDF library is installed, and Czech needs an embedded font).
- **What kind of document**: a provider that is not a VAT payer issues a *receipt* (`doklad o přijaté platbě`), which is all that exists to issue - it has no VAT to show. A VAT payer needs a real tax document (rate, tax base in CZK at the CNB rate, date of the taxable supply, OSS for other EU countries) which **this application does not produce**: for `vat_payer: true` the document is titled a payment *confirmation*, says it is not a tax document, and the tax document has to come from the accounting system. Refunds (and the credit notes they need) are not handled either.
- **Why payments are off is said out loud** (`payments_status.py`): `GET /payments` says `enabled: false` when any of three things is missing - the `stripe_payment_gate` module in `modules.json`, `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` in `.env`, the provider's details (`ProviderConfig.missing_fields()`: name, ico, address, email) - and the frontend then leaves every payment option out **without a word**, which looks like a bug (it already bit once). So the same conditions, one `Problem` each (`problems()` is the single source of truth; `router.gateway_enabled` and `/payments` are derived from it, and a parametrized test keeps the public flag equal to `not problems(...)`), are reported in two places: **one console warning at startup** (`log_payments_status`, the boards manifest's `on_startup` hook - lists every reason and the file to edit, or `Payments are on`) and **a notice for administrators above the tabs of `/moderation`** (`PaymentsStatusNotice.tsx`, `GET /manage/payments-status`, shown only while payments are off). Both report only whether a key is *set*, never its value (a test pins it). The config is read once at startup, so the notice and the log both tell the reader to restart the backend after editing. When adding a fourth condition for payments, add it to `payments_status.problems()` and to the frontend's `admin.payments.problem.*` texts - nowhere else.
- **Who issues**: `invoicing.provider` in `boards.json` (name, IČO, address, email are the minimum) must be filled in or **payments are refused and `GET /payments` says off** - a document without an issuer would be worthless, and the money would already be taken. It is the same person as `provider` in the frontend's `legal.json`; `tests/test_modules_boards_legal.py` fails if the two differ. Two more things for a lawyer: § 1824 of the Civil Code wants the terms on a durable medium and the email only *links* them, and the email is HTML only (no plain-text alternative).
- **Searching categories** (`GET /categories?q=`, `search.py`, the search box in `CategoriesList.tsx`): a category is found when its title *or* description contains **every word** of the query, ignoring case and diacritics ("priroda" finds "Příroda", and the other way round). The text searched is `Category.search_text` - title and description through `search.normalize_text` (NFKD, case-folded, whitespace collapsed) - filled by the model's insert default (`_category_search_text`), so a row made any way is searchable; **title and description are never edited**, so the insert is the only moment, and anything that starts editing them must rebuild it. The migration `bd7b5715b84c` backfills existing rows with its own *copy* of the normalizer (a migration keeps doing what it did) and a test keeps the two equal. Matching is `LIKE` with `app.services.sql.like_pattern` (so `%`, `_` and `\` in a query are literal), no database extension; a blank `q` is no search; `q` is at most 100 characters (422). **The order is the one the list always had - most published posts first, then title - with or without a search**: a search narrows, it does not rank (hidden / blocked posts do not count; a blocked category is not found). `search_text` is never in `CategoryOut`. The frontend list keeps its search in its own state, except on `/categories`, whose page passes `query` / `onQueryChange` so it lives in the address (`?q=`, replace-state), and the page is `noindex` while a search is on (its canonical address, which `usePageMeta` takes without the query, is the plain list); the fetch waits 300 ms after typing stops, an answer for a search that is no longer the shown one is dropped, and "Load more" continues the same search by offset.
- **Sitemap and robots.txt**: `GET /api/modules/boards/sitemap.xml` (`sitemap.py`) lists `/`, `/categories`, the legal and contact pages of the modules that are *enabled* (`MODULE_PAGES` - add a public page of another module there) and every published category (`lastmod` = its newest published post, else its creation), under `Settings.frontend_url` (so `FRONTEND_URL` must be the real address), at most 50 000 URLs, cached an hour. The static frontend cannot write it, so **the web server has to map `/sitemap.xml` to that endpoint** (`scripts/install.sh` does for a fresh install; an existing server needs the same `location = /sitemap.xml { proxy_pass ...; }` by hand; the Vite dev server proxies it). `robots.txt` is not a file in `public/`: `frontend/vite.config.ts`'s `robotsTxt` plugin writes it at build (and serves it in dev) because its `Sitemap:` line must be absolute, from the build's `VITE_APP_URL`; its `Disallow` list is the real private routes - **a new private page goes in `ROBOTS_DISALLOW` and gets `noindex: true`**. A page that shows nothing to a crawler (a category that does not exist, the 404 page, search results) is `noindex` too, since the server answers 200 for every address. `usePageMeta` also takes `jsonLd` (schema.org; the home page has `WebSite`, the category list a breadcrumb, a category `CollectionPage` + breadcrumb), cuts every description to ~160 characters at a word (`clipDescription`) and fills the Twitter tags; `index.html` carries the same defaults for link-preview bots and crawlers that do not run JavaScript (Czech, `%VITE_APP_URL%` for the absolute Open Graph image) and a `<noscript>` text. The share image is `logo.png`, the template's WFB mark: a 1200x630 image of the application's own would make link previews better. There is one URL per page for both languages (the language is the visitor's choice, not part of the address), so there is no `hreflang`; and the pages are rendered in the browser, so a crawler that does not run JavaScript sees only `index.html` - server-side rendering or prerendering would be the next step.

## Repository purpose

This repository hosts a **family of applications built on one shared core**, rather than a single deployable app. The reusable foundation — `backend/` (FastAPI), `frontend/` (Vite/React), and `scripts/` (build + deployment tooling), wired to a separate, shared authorization service at `auth.withfbraun.com` (see "Authorization" below, which is the largest and most actively-evolving part of it) — is developed on the `core` branch. Each application lives in its own branch and pulls in `core`'s changes, so a fix or feature that belongs to every app is made once, on `core`, instead of being duplicated per application. Components remain independently versioned and deployed within any given branch — see "Independent versioning" below.

### Branch structure

- **`core`** — the shared foundation described by the rest of this file (backend, frontend, scripts, auth integration). Cross-cutting work happens here first.
- **Application branches** — one per real app, branched **directly from `core`** (the `new-app` skill automates this). They diverge with app-specific code (models, pages, config) while periodically merging in updates from `core`.
- **`template_app`** — also branched from `core` and kept in sync with it, but *not* the fork point for the applications above. It carries forward the repository's original, standalone template role: a generically-branded starting point for cloning and renaming into a one-off app outside this family. Don't confuse the two workflows.

**Branches synced from `core`:** `template_app`, `slavickovy-knihohratky`, `api-hub`, `thoughtauction`, `wfb-freelancer`, `showing_pub`, `homerepository`. This list grows as applications are added — the `new-app` skill appends to it automatically when it forks one; the `new-module` skill reads it (not a hardcoded branch list) to know where to roll a new module out to. Keep it current if a branch is added or retired by hand.

When working on a branch other than `core`, treat app-specific code you find as intentional local divergence — don't "fix" it back to match `core` unless that's the actual task.

- **Every backend change needs test coverage.** After adding or modifying anything under `backend/app/`, create or update the matching test(s) under `backend/tests/` in the same change — do not leave backend code changes untested.

## Architecture

### Backend: config, routing, DB, logging, email
- All settings load through `app/config.py`'s `Settings` (pydantic-settings), sourced from `backend/.env` (see `.env.example`). `BASE_DIR` there anchors all relative paths (env file, log dir) to `backend/` regardless of the process's cwd. `get_settings()` is `@lru_cache`d — a running process never picks up `.env` changes without a restart (`uvicorn --reload` only watches `.py` files, not `.env`).
- All REST routes are mounted under the `/api` prefix via `app/api/router.py`, which aggregates sub-routers (`app/api/public/version.py`, `app/api/auth/router.py`, `app/api/account/router.py`). Add new endpoints as their own `APIRouter` and wire them into `api_router` there, rather than adding routes directly in `main.py`.
- DB access is async-only: SQLAlchemy's async engine + `asyncpg` (the `DATABASE_URL` scheme is `postgresql+asyncpg://`, which has no sync counterpart — don't reach for `psycopg2`-style sync sessions). `app/models/base.py` has an empty `Base`; `app/models/user.py`'s `User` is the only concrete model so far (see Authorization below) — holds just the identity link (`auth_sub`) plus fields genuinely local to this app (an illustrative `nickname` — see the local account resource below — and `is_admin`, see below). Identity fields (email, name, role, ...) stay owned by the auth service and are read fresh from the JWT / `GET /api/auth/me`, never duplicated here.
- Alembic is wired for the async engine (`alembic init -t async`). `alembic/env.py` pulls the connection string from `Settings.database_url`, not from the static placeholder in `alembic.ini`, and sets `prepend_sys_path = %(here)s` so `import app` resolves regardless of invocation directory. Any new model must be imported in `alembic/env.py` (see the `from app.models.user import User` line there) or autogenerate won't see its table.
- Logging is configured once at import time in `main.py` via `configure_logging()` (`app/logging_config.py`) — a `TimedRotatingFileHandler` (fixed daily rotation, `when="midnight"`) + console handler attached to the root logger. Settings field names match `.env.example`'s `LOGGING_*` keys exactly: `logging_level`, `logging_dir`, `logging_filename`, `logging_days_history` (backup count), `logging_message_format`. Note `.env`/`.env.example`'s format string's `\t` is a literal backslash-t (two characters), not an actual tab — `.env` files don't interpret string escapes the way Python source does, and `Settings` passes the value straight to `logging.Formatter()` unmodified. That's a property of the configured value, not a bug to fix in code; change it in `.env` (to a real tab or something else) if the literal `\t` in log output isn't wanted.
- Email goes through `app/services/email.py`'s `send_email()`, built on `fastapi-mail`. Connection defaults come from `Settings` (`MAIL_*` in `.env`), but every `ConnectionConfig` field can be overridden per call via kwargs (e.g. a one-off `MAIL_FROM`). `MAIL_SUPPRESS_SEND=true` still builds and dispatches the message internally (so tests can assert on it via `FastMail(...).record_messages()`), it just skips opening a real SMTP connection.

### Backend: authorization (auth.withfbraun.com)
This template doesn't implement its own user auth — it's a **backend-for-frontend proxy** in front of a separate, shared auth service. The browser only ever talks to this app's own `/api/auth/*`; only this backend holds the `X-Api-Key` secret and talks to `auth.withfbraun.com` directly. That service's OpenAPI spec (`https://auth.withfbraun.com/openapi.json`) is the authoritative contract and **is actively evolving** — two real discrepancies have already been found between it/its manual and live behavior (an endpoint that didn't exist yet, a response shape that didn't match the docs). Re-fetch and diff against it before trusting any assumption about paths or schemas; don't rely on memory of a previous session's findings.

- `app/services/auth_client.py`'s `AuthClient` (module-level singleton `auth_client`, closed in `main.py`'s `lifespan` alongside the DB `engine`) wraps every call to the auth service: `register`, `login`, `refresh`, `logout`, `get_me`, `update_me`, `get_group_attributes`, `update_group_attributes`, `get_public_key`, `get_group_info`, `get_consent_info`, `grant_consent`, `reject_consent`. **`X-Api-Key` is mandatory on every single method** (`_require_api_key()` raises `RuntimeError` immediately if it's empty, rather than silently sending an empty header — the auth service treats a missing/empty key as "no application context" and skips its consent check entirely, which is a real security-relevant footgun, not just a style choice). `login()` is the one method that returns the raw `httpx.Response` instead of raising on non-2xx: its caller needs to distinguish "200 with tokens" from "403 consent_required" itself.
- `app/security/jwt.py` verifies access tokens locally (RS256) against a public key fetched once from `GET /api/auth/public-key` and cached in a module-level variable guarded by an `asyncio.Lock` — deliberately not `functools.lru_cache` on an `async def`, which would cache the coroutine object rather than its awaited result. Uses **PyJWT**, not the auth service's own manual's suggested `python-jose` (python-jose has a disclosed, unpatched `alg=none` bypass, CVE-2025-61152, and is broadly unmaintained — FastAPI's own docs have moved to PyJWT too).
- `app/api/deps.py`'s `get_current_user` composes JWT verification with the local DB: resolves (or creates, via `INSERT ... ON CONFLICT (auth_sub) DO NOTHING` + re-select — not a naive check-then-insert, which would race two near-simultaneous first requests from the same new user) the `User` row for the verified `sub` claim. `require_admin` builds on it and lets only users with the local `User.is_admin` flag through (403 otherwise) - **this app's administrators are decided by that flag, never by the JWT's `role_name`**: the role belongs to the user across every application on the shared auth service, so an auth-service "admin" would otherwise administer every app. `is_admin` is set directly in the database (default `false`); it is exposed read-only on `GET /api/auth/me` and `GET /api/account/me` and deliberately absent from `AccountUpdate`, so nobody can promote themselves. Feature modules gate their admin endpoints on `require_admin` too (e.g. `event_calendar`).
- `app/api/auth/router.py` exposes `register` / `login` / `refresh` / `logout` / `me` (`GET`) / `update_me` (`PATCH /me`) / `get_group_attributes` + `update_group_attributes` (`GET`/`PATCH /me/group-attributes/{group_id}`) / `group-info` / `consent/{id}/grant` / `consent/{id}/reject`, matching exactly what `frontend/src/context/AuthContext.tsx`, `Account.tsx` and `api/client.ts` call. Non-obvious points:
  - `GET /me`'s upstream response (`MeResponse`) always has `consent_required` + `application_group_id`; `user` is populated only once consent is granted. Our own `/me` converts `consent_required: true` into a 403 with that same `{consent_required, application_group_id}` shape — matching `/login`'s own 403 convention, so the frontend has one code path for both (this also covers entry points that skip `/login`'s check, e.g. Google OAuth). On success, `application_group_id` is merged into the flat response too (`{**user, application_group_id}`), so the frontend can call the group-attributes endpoints below without a second round trip; `PATCH /me` doesn't repeat this merge since that id never changes on a profile edit. `result.get("user") or result` is a defensive fallback for an earlier observed state where a granted response had no wrapper at all — cheap insurance, shouldn't trigger against the currently-published schema.
  - `PATCH /me/group-attributes/{group_id}` **replaces the entire upstream `user_data` object — it is not a partial merge.** Callers (see `Account.tsx` below) must fetch the current value first and send the full merged object. The backend treats `user_data` as a fully opaque JSON blob; the shape it *should* have is defined client-side (`public/config.json`, see below), not here.
  - The auth service's own `UserGroupAttributesPublic` schema documents itself as "user_data only, system_data is hidden" — `system_data` is not reachable through any endpoint this app has credentials for, at any layer, confirmed against the live OpenAPI spec. Don't build backend support for it.
  - Consent is resolved through this template's **own** `/consent` page (`frontend/src/pages/Consent.tsx`), not the auth service's hosted one — it calls `GET /api/auth/group-info` (X-Api-Key only, no user token) to render the scopes, then `POST /api/auth/consent/{id}/grant` or `.../reject`.
- `app/api/account/` is a **separate, local-only** resource (`GET`/`PATCH /api/account/me`) for fields this app owns outright (currently just `nickname`). It depends only on `get_current_user` and the local DB session, and deliberately has **no import of `auth_client` anywhere in the package** — that absence is itself the enforcement that editing local account data can never reach the auth service. When adding real app-specific fields, keep this separation: local data goes through `app/api/account/`, identity/profile data goes through the auth-service-proxying endpoints above.
- Testing patterns specific to this layer (see `tests/conftest.py`): `generate_rsa_keypair()` / `make_access_token(sub=..., **claims)` for signing test JWTs without touching the real service; `respx` mocks every upstream HTTP call (no test should ever hit `auth.withfbraun.com`); route tests that need both a real JWT dependency chain *and* the DB (e.g. `/me`) use `httpx.AsyncClient(transport=ASGITransport(...))` instead of the `client` (`TestClient`) fixture — `TestClient` drives the ASGI app from a separate thread with its own event loop, which conflicts with `db_session`'s connection (bound to the test's own loop); `ASGITransport` keeps everything on one loop. `pytest.ini` also sets a **session-scoped** asyncio event loop for the same underlying reason: `app/database.py`'s `engine` is a module-level singleton whose connection pool can't be split across per-test loops.

### Cross-cutting: backend and frontend version independently
- `backend/version.json` and `frontend/public/version.json` are separate, independently-maintained version markers — there is no shared version number between the two components.
- `GET /api/public/version` reads and returns `backend/version.json` verbatim.
- The frontend's `/version` page (`frontend/src/pages/Version.tsx`) fetches both that endpoint and its own `/version.json`, and flags a mismatch whenever their major.minor versions differ, using the shared `parseMajorMinor`/`compareVersions` helpers in `src/utils/version.ts`.
- `scripts/build.py` packages and tags backend/frontend releases separately (git tags `B-x.y.z` / `F-x.y.z`), so the two genuinely drift independently in normal operation — the `/version` page's compatibility check is the runtime signal for when that drift matters.
- `backend/release_news.json` and `frontend/public/release_news.json` carry the same independence into changelog data: `{unreleased: string[], releases: [{version, release_date, changes}]}`. `GET /api/public/release-news` reads and returns the backend's file verbatim (same pattern as `/version`); the frontend fetches its own `release_news.json` directly, since it's static, in `public/`. The `/release-news` page groups each side's `releases` by major.minor (via the same `src/utils/version.ts` helpers) and renders every generation as a two-column row — a generation with entries on *both* sides gets a "compatible" highlight, one side missing entries reads as an empty column, so (in)compatibility is visible without comparing dates.
- **Every change appends to the relevant `unreleased` array** (see Workflow requirements above). `scripts/build.py`'s `seal_release_news()` moves a component's accumulated `unreleased` entries into a new dated release under the resolved version at STABLE build time, then clears `unreleased` (a no-op, so safe to re-run, if nothing's pending). It edits the local working-tree file, not the git ref being archived — commit the sealed file and create the release tag from that commit *before* running the build, or the archived package won't include the sealed entry.

### Frontend: routing, auth flow, styling
- Routes are declared in `App.tsx` (react-router-dom) and wrapped by `AuthProvider` + `BrowserRouter` in `main.tsx`; page-level chrome (nav bar + language switcher) comes from `components/Layout.tsx`. Pages: `HomePage.tsx` (`/`, public), `Login.tsx` (`/login`, email/password + "Continue with Google"), `Register.tsx` (`/register` — registration alone issues no tokens, per the auth service's own design, so success just shows a confirmation + a link to `/login`, it does not log the user in), `Account.tsx` (`/account`, see below), `OAuthCallback.tsx` (`/oauth/callback` — extracts tokens Google's flow appends as query params), `Consent.tsx` (`/consent`), `ConsentRejected.tsx` (`/consent-rejected`), `Version.tsx` (`/version`, public diagnostic page).
- `Layout.tsx`'s nav bar is the only way to reach `/account` / `/register` / `/login` besides typing the URL directly — it swaps between Login/Register (logged out) and Account/Logout (logged in) links based on `useAuth().user`, plus a CS/EN language switcher (see i18n below).
- `api/client.ts` owns the API base URL (`VITE_API_URL`) and the JWT access/refresh token lifecycle: `apiFetch()` attaches the bearer token and transparently retries once via `/api/auth/refresh` on a 401.
- **Consent redirect is centralized in `AuthContext.tsx`**, not left to callers: both `login()` (on a 403 `consent_required` from `/api/auth/login`) and `loadUser()` (on the same shape from `/api/auth/me`) call an internal `redirectToConsent()` that navigates to `/consent?group=<id>&redirect=<target>`, preserving tokens (the user *is* validly authenticated, just missing consent — don't `clearTokens()` on this path). Four constraints here were all found by live testing against the real service, not by inspection — preserve them when touching this file:
  - `redirectToConsent`'s redirect target falls back to `/` whenever the *current* page is `/login`, `/oauth/callback`, or `/consent` itself, rather than blindly capturing `window.location.pathname`. Consent is very often detected from *within* `login()` itself (not just on page load for an already-protected route), and at that moment the "current page" is always `/login` — capturing it verbatim sends the user back to an empty login form after granting, not anywhere useful.
  - `AuthProvider`'s initial-session-restore effect (the one that calls `loadUser()` on mount if a token already exists) has an **empty dependency array (`[]`), not `[loadUser]`**, and that's intentional. `loadUser`'s identity depends on `navigate` (via `redirectToConsent`), which react-router doesn't guarantee stays referentially stable across navigations; depending on `[loadUser]` let this mount-only check silently re-fire on unrelated route changes, redundantly re-querying `/me` and, if consent was pending, re-triggering the consent redirect using whatever URL it had *just* redirected to as the new target (a doubly-nested `redirect` query param).
  - `Consent.tsx` calls `loadUser()` again right after a successful grant, before navigating away. `AuthContext`'s `user` stays `null` through the entire consent-required window (`loadUser()` returns early without setting it), so without this refresh, navigating to any page that guards on `useAuth().user` (e.g. `Account.tsx`) would immediately bounce back to `/login` on the stale `null`.
  - Both `login()` and `OAuthCallback.tsx` only navigate to `/` when `loadUser()` reports it actually loaded the user (`loadUser()` returns a `boolean`) — navigating unconditionally after a successful token exchange was a real bug (a successful OAuth login would fire `navigate('/')` right after `loadUser()` had already redirected to `/consent`, canceling it).
- Google OAuth needs no backend involvement at all: the browser is redirected straight to `${getAuthUrl()}/auth/google?redirect_uri=...`, the auth service handles the whole exchange with Google, and redirects back to `/oauth/callback` with tokens as query params directly. `VITE_AUTH_URL` is what `getAuthUrl()` reads for this — it's the one place the frontend needs to know the auth service's own public URL, since a browser redirect can't be proxied through the backend like the password-based endpoints are. (`frontend/.env.example` correctly points this at `https://auth.withfbraun.com` and no longer defines an unused `VITE_API_KEY` — both were flagged and fixed in an earlier pass; don't reintroduce either into runtime frontend code. `build.py` does write its own hardcoded `VITE_API_KEY` for a completely separate reason — see Deployment below.)
- Tailwind is v4, CSS-first: there is no `tailwind.config.js`. `src/index.css` just does `@import "tailwindcss"` plus a handful of hand-written base styles, and the `@tailwindcss/vite` plugin (in `vite.config.ts`) handles content detection automatically.
- `CORS_ORIGINS` in `backend/.env.example` (and the `Settings.cors_origins` default) match the frontend dev server's actual default port, `["http://localhost:5173"]` — keep these in sync if either default port ever changes.

### Frontend: internationalization (i18n)
- `react-i18next` + `i18next-browser-languagedetector`, initialized once in `src/i18n/index.ts`. `SUPPORTED_LANGUAGES` (currently `['cs', 'en']`) is the **single source of truth** for which languages ship — `Layout.tsx`'s language switcher iterates over it and `applyUserLanguage()` (below) checks against it; don't hardcode a separate language list anywhere else. Detection order is `localStorage` before `navigator`, with `cs` as `fallbackLng` (this template originates from a Czech-first product) — `supportedLngs` must stay pinned to the same list `resources` actually ships, or an unrecognized locale resolves to a partial/missing bundle.
- Translation keys are namespaced per page in `src/i18n/locales/{cs,en}.json` (`login.*`, `account.*`, `common.*` for shared strings, etc.) — every page component calls `useTranslation()` and reads its own strings via `t('page.key')`; there's no untranslated hardcoded copy anywhere in `src/pages/`.
- `applyUserLanguage(languageCode)` (exported from `src/i18n/index.ts`) is a fallback **cascade**, not a straight assignment: the signed-in user's own `language_code` if this app ships that language, else `'en'` if that's shipped, else **leave the current language untouched** (whatever was active before — a manual switcher choice or the detector's result). It's called from `AuthContext.tsx`'s `loadUser()` (covering session restore, login, and Google OAuth — every path that resolves who the user is) and again from `Account.tsx` after saving the Profile card, so editing `language_code` there takes effect immediately without a reload.

- `src/hooks/usePageMeta.ts` is what every page calls for its search-engine and link-preview identity: document title (suffixed with `nav.brand`), description (the page's own, else `meta.description`), canonical URL, Open Graph / Twitter tags, the robots directive and `<html lang>` (kept in step with the active language). It names no application - each one sets `nav.brand` and `meta.description` in its own `cs.json` / `en.json`. Pass `noindex: true` on pages that must stay out of search results (sign-in, account, administration, diagnostics - the core's own already do), and `jsonLd` for the page's structured data (one reused `<script type="application/ld+json">`); it also exports `absoluteUrl(path)` and `clipDescription(text)`. The tags are written client-side, so crawlers that run JavaScript see them per page, while link-preview bots only see what `index.html` carries.

### Frontend: theming (light/dark mode)
- Dark mode is **class-based, not OS-preference-based**: `src/index.css` declares `@custom-variant dark (&:where(.dark, .dark *));` (Tailwind v4's CSS-first equivalent of `darkMode: 'class'`), so every `dark:` utility across the app activates only when a `.dark` class is present on `<html>` — it deliberately does not follow the OS's `prefers-color-scheme`.
- `src/context/ThemeContext.tsx`'s `ThemeProvider`/`useTheme()` owns two pieces of state: `darkMode` (the active local theme — defaulting to `false`/light, toggling the `.dark` class on `document.documentElement` and persisting to `localStorage`'s `dark_mode` key in a `useEffect`) and `profileDarkMode` (the last known value of the signed-in user's **profile-stored** preference, `boolean | null` — `null` until it's been fetched or set at least once). Both live in context, not in any one page's local state, specifically so every consumer — either `ThemeToggle` instance, the Account page's stored-value display, and its save payload — reads and writes the same shared value regardless of which one triggered a change. This provider works standalone for a logged-out visitor (`profileDarkMode` just stays `null`) — populating it for a signed-in user is layered on top in `AuthContext.tsx` and `Account.tsx`, not inside `ThemeContext` itself.
- `main.tsx` nests `<ThemeProvider><AuthProvider><App /></AuthProvider></ThemeProvider>` — **that order matters**: `AuthContext.tsx`'s `loadUser()` calls `useTheme()` to apply the server-stored preference once the user resolves, so `ThemeProvider` must already be an ancestor.
- The stored preference lives at `user_data.darkMode` (`true`/`false`) via the existing group-attributes endpoints — **not `system_data`**, even though the field is conceptually closer to an app setting than user profile data. `system_data` is confirmed inaccessible to this app's credentials (see Authorization above); this was a deliberate scope decision, not an oversight, when this feature was built.
- `src/theme.ts`'s `persistDarkModePreference(groupId, darkMode)` is the write path: fetch the current group-attributes, merge `darkMode` into the existing `user_data` (PATCH replaces the whole object, same constraint as the config.json attributes below), then PATCH. It's best-effort and swallows errors — the local theme (already applied via `ThemeContext`) doesn't depend on the server save succeeding.
- `src/components/ThemeToggle.tsx` is one shared toggle switch, rendered in both `Layout.tsx`'s header nav and `Account.tsx`'s dedicated theme section, so the two controls behave identically: on click it flips the local theme immediately via `setDarkMode`, and — only when signed in (`user?.application_group_id` is set) — fires `persistDarkModePreference` *and* `setProfileDarkMode(next)` in the same click, optimistically (not awaiting the PATCH), with no separate save step. Because `setProfileDarkMode` writes to `ThemeContext` rather than a component-local callback, it doesn't matter which instance of `ThemeToggle` is clicked — both the header's and the Account page's stay in sync immediately. The thumb's own positioning deliberately avoids `position: absolute` with no explicit `left`/`right` (that renders on the wrong side, since the browser falls back to an ambiguous "static position") — it uses `inline-flex items-center` on the track and `inline-flex items-center justify-center` + `translate-x-*` on the thumb instead, which positions deterministically; the latter also centers the sun/moon glyph the thumb renders for the active mode.
- `AuthContext.tsx`'s `loadUser()` best-effort fetches group-attributes after resolving the user and calls both `setProfileDarkMode(stored)` (`stored` defaulting to `false` when unset) and, **only if the field is an explicit boolean**, `setDarkMode(data.user_data.darkMode)` — an unset preference (new user, or a config predating this feature) leaves the *active* theme untouched (whatever was already active — localStorage value or a pre-login manual toggle) rather than forcing a reset to `false`, while still seeding `profileDarkMode` so the Account page's display is correct from the start.
- `Account.tsx` renders a third, visually separate block below the two `<form>` cards (a plain `<div>`, not inside the Profile `<form>` — it has no Save button of its own since `ThemeToggle` already saves on click): it shows `storedDarkMode` (read straight from `ThemeContext`'s `profileDarkMode`, defaulting to `false`) labeled as "stored in profile", contrasted against the currently-active `darkMode` from `useTheme()`, surfacing a divergence warning whenever they differ. Because both values come from the same shared context, this only fires for a *genuine* mismatch (e.g. a stale `localStorage` value from a previous session, not yet reconciled) — not merely because some other component's toggle click hasn't been reflected here yet. Its own group-attributes fetch (on mount) seeds `profileDarkMode` via `setProfileDarkMode`, and a separate `useEffect` mirrors `profileDarkMode` back into `attributeValues.darkMode` (the state object the Profile card's Save button PATCHes) whenever it changes, so a plain Save click never PATCHes back a stale value even if the theme was toggled from the header since the page loaded.

### Frontend: configurable auth.user attributes (`public/config.json`)
- `public/config.json` declares extra, app-specific fields to render on top of auth.user's core profile fields on the Account page's Profile card — each entry has a `key`, a `bucket` (`user_data` or `system_data`), a `type` (`text` / `number` / `boolean` / `date`), a `required` flag, and an `i18nKey`. It's fetched at runtime via `loadUserAttributes()` in `src/config/userAttributes.ts` (it's static, in `public/`, not a build-time import — editing it doesn't require a rebuild).
- **Only `bucket: "user_data"` entries ever render or save.** `system_data` entries are dropped by `loadUserAttributes()` with a `console.warn`, not silently ignored — this app's credentials can never read or write `system_data` on the auth service (see Authorization above), so a `system_data` config entry would otherwise look like a real field that silently fails to save. A config file may still declare `system_data` entries for documentation purposes; don't build a code path that tries to render one.
- `DynamicAttributeField.tsx` renders one control per attribute based on `type`. Saved values round-trip through `PATCH /api/auth/me/group-attributes/{group_id}` — since that endpoint replaces the whole `user_data` object (see Authorization above), `Account.tsx` always sends the full known set of attribute values on save, not just whichever one changed.
- `Account.tsx`'s two cards never cross endpoints: the Account card (`nickname`) only ever calls `/api/account/me`; the Profile card (core fields + the config-driven attributes above) only ever calls `/api/auth/me` and its group-attributes endpoint. Each card has its own independent saving/error state so one failing never blocks the other. One nuance worth preserving: controlled inputs store an unset field as `''` (React inputs can't hold `null`), but the auth service validates fields like `birth_date` as a real date-or-absent and rejects `""` outright — `Account.tsx`'s `blankToNull()` converts blanks to `null` right before the `PATCH /api/auth/me` request.

### Feature modules (pluggable, per-application)
This template ships the **structure** for optional feature modules (e.g. an administration area, reservations, orders) that can be pre-built once, then turned on/off and customized per application — it ships **no concrete modules of its own**. Both sides follow the same shape: a module is a self-contained package under a conventional folder, auto-discovered without editing any shared wiring file, and gated by its own enable-list.

- **Backend** (`app/modules/<key>/`): a subpackage whose `__init__.py` exposes `manifest = ModuleManifest(key=..., router=..., ...)` (`app/modules/base.py`; an optional `on_startup` callable is run once at startup for each *enabled* module by `registry.run_startup_hooks`, called from `main.py`'s `lifespan` - for a check that should be said in the console, like the boards' payments status; a hook that raises is logged and skipped, never stops the startup). `app/modules/registry.py`'s `discover_modules()` walks every subpackage of `app.modules` via `pkgutil` and imports it; a subpackage with no `manifest`, or whose `manifest.key` doesn't match its folder name, is skipped with a `logger.warning` rather than crashing the app. `load_enabled_module_keys()` reads the `enabled` array of keys from **`backend/modules.json`** — git-tracked, same `{"enabled": [...]}` shape as the frontend's `public/modules.json` — and `get_enabled_modules(keys)` filters discovery down to it; `app/api/router.py` loops over that and mounts each enabled module's router under `/api/modules/<key>` (or `manifest.prefix`, if set). **Enabling/disabling a module never touches the DB schema** — `import_all_module_models()` is called once from `alembic/env.py` and imports `<module>.models` for *every discovered* module regardless of enabled state, so migrations stay identical across deployments no matter which modules a given application has turned on; enabled/disabled only gates whether a module's router gets mounted. This is what lets a module be dropped into `app/modules/` and picked up everywhere (routing, migrations) without hand-editing `router.py` or `alembic/env.py` again. The module selection deliberately does **not** live in `Settings`/`.env` (it used to be `ENABLED_MODULES` there, now ignored): `.env` is untracked and shared by every branch checked out in the same working tree, so switching to another application branch silently kept the previous one's modules. A missing `modules.json` means no modules; a malformed `enabled` value raises at startup; and `tests/test_modules_registry.py` fails the suite if the branch's committed file enables a key that no discovered module has.
- **Frontend** (`src/modules/<key>/index.tsx`): default-exports a `ModuleDefinition` (`src/modules/types.ts`) — `key` (must match the folder name and an entry in `public/modules.json`'s `enabled` array), `routes` (`{path, element}[]`, same shape as react-router-dom's `<Route>`), optional `nav` (`{to, labelKey, requiresLogin?}[]` - rendered as pills in the header, the current page filled in; `requiresLogin` hides an item from a signed-out visitor, as for the boards' "my posts" and "my payments"; the desktop nav appears from the `lg` breakpoint, below it the menu button opens the same pills), optional `footerLinks` (same shape, rendered as a link row in `components/Footer.tsx`, which calls `useEnabledModules()` itself rather than receiving modules from `Layout`), optional `headerWidget`, optional `locales` (per-language translation objects). `src/modules/registry.ts` uses Vite's `import.meta.glob('./*/index.tsx', { eager: true })` to import every module at startup with no per-module import statement anywhere else, registers each one's `locales` as its own i18next namespace (`i18n.addResourceBundle(lang, key, ...)`) **unconditionally** — same rationale as the backend always registering models: cheap, and keeps enable/disable a pure routing/nav concern — and exposes `useEnabledModules()`, a hook that fetches `public/modules.json` once (cached) and returns only the enabled subset. `App.tsx` spreads `module.routes` into `<Routes>` and `Layout.tsx`'s `Nav` spreads `module.nav` into the header, both driven by that hook — neither needs to change when a module is added, removed, or toggled. A nav item's `labelKey` must be namespaced as `"<moduleKey>:<key>"` (i18next's default `nsSeparator`) to resolve against that module's own bundle rather than the core `translation` namespace.
- **`backend/modules.json` and `frontend/public/modules.json` are independent config files, kept in sync manually per branch** — each application branch commits its own selection in both, `core` ships both as `[]`. Same independence as the rest of backend/frontend config in this template (see "Cross-cutting" above). There's no runtime cross-check; enabling a module on one side but not the other will produce a UI with no backend to call, or API routes with no frontend entry point.
- **A module's own non-secret settings (texts, switches) go in a git-tracked `backend/modules/<key>.json`**, loaded and validated by the module itself — for the same per-branch reason as `modules.json`. Secrets and per-server values (SMTP, `CONTACT_MAIL`, Stripe keys) stay in `.env`. `kontaktni_formular.json`: `send_reply`, `default_language`, and `reply_templates.<lang>.{subject,body}` for the sender's confirmation email. The template is picked from the request's `language` (the frontend sends `i18n.resolvedLanguage`): exact match first, then the primary subtag, else `default_language`. Placeholders are limited to `{sender_name}`, `{reply_to}`, `{subject}`, `{message}`, and all of it is validated on load (`app/modules/kontaktni_formular/config.py`), with a test guarding each branch's committed file. The same file holds what the contact page (`/contact`; `/kontakt` redirects) shows around the form: `page.<lang>.{title,intro,aside}` (blank line = new paragraph; a language without texts falls back to `default_language`'s, then to none) and `show_email` (off by default: whether `CONTACT_MAIL`, where the form is delivered, is shown as a contact detail). The per-server details are `.env`'s - `CONTACT_ADDRESS`, `CONTACT_GITHUB_URL`, `CONTACT_LINKEDIN_URL`, each shown only when set, links only when they are http(s) URLs - and the page gets all of it from the public `GET /api/modules/kontaktni_formular/info?language=`, which exposes only those fields. Nothing configured, or the request failing, leaves the page as the plain form. `event_calendar.json` holds `page_size` (editors are the app's `is_admin` users, see `require_admin` above). Uploaded images (`Settings.uploads_dir`, `UPLOADS_DIR` in `.env`, a per-server path) belong to the `articles` module (`uploads_dir/articles/`).
- **`crm` is an administrators-only module** (partners -> tasks -> invoice PDFs; no config file, nothing public). The router itself carries `require_admin`, so every route is gated and a later one can't forget it; `tests/test_modules_crm_router.py` walks every route as anonymous and as a non-admin. Invoice PDFs are checked (declared `application/pdf` *and* a `%PDF-` header, max 10 MB), stored as `<uuid>.pdf` under `Settings.uploads_dir`/`crm/` and readable only through `GET /invoices/{id}/file` (authenticated, `attachment`, `no-store`) - unlike `event_calendar`'s public images there is no upload URL, and the frontend downloads the blob with the bearer token. A partner with tasks and a task with invoices answer 409 on delete (partners are archived instead). The UI is shown when `useAuth().user.is_admin` (from `GET /api/auth/me`), as a `headerWidget` icon rather than a `nav` entry, which would show to every visitor; every page is wrapped in `CrmGate`.
- **Module dependencies are advisory and logged, never enforced.** `ModuleManifest.requires` (backend, `app/modules/base.py`) and `ModuleDefinition.requires` (frontend) list the keys of modules a module only works with. `registry.check_module_dependencies()` runs once from `app/api/router.py` and logs a warning for every enabled module whose requirement isn't enabled (and for a requirement no module provides - a typo), and `findMissingRequirements()` in `src/modules/registry.ts` does the same with one `console.warn` per problem when `modules.json` is first read. Neither side ever stops, hides or disables anything: a half-switched-on feature must be visible in the log, not take the app down.
- **Frontend slots** let a module extend another module's pages without that module knowing about it. A module renders `<ModuleSlot name="…" context={…} />` (`src/modules/ModuleSlot.tsx`) in its pages and documents the slot name and `context` shape next to it; any *enabled* module contributes a component to it through `ModuleDefinition.slots` (a map of slot name → component receiving `{ context }`), in module-folder-name order, and nothing renders when none does. `ModuleSlot` and `useEnabledModules` live in `src/modules/moduleStore.ts`, which holds the discovered list and the enabled keys and imports no module; `registry.ts` (which imports **every** module through `import.meta.glob`, adds their translations and hands the list to the store) is imported only by the entry point - a module, or anything a module imports, importing `registry.ts` would form an import cycle that kills the app at start-up depending on which of the two a page imports first (guarded by `backend/tests/test_frontend_module_imports.py`; it surfaced on an application whose home page imports a module's exports). This is how a module built on top of another (the event calendar on articles) puts its UI on the lower module's pages while the lower module stays independent. Slots defined so far: `article.detail`, `article.editor` (see `articles` below), `event.actions`, `event.manage`, `event.editor` (see `event_calendar` below), `crm.partner` (see `tickets` below).
- **Backend hooks and background tasks** are the backend side of the same idea (`ModuleManifest.hooks` / `.background_tasks`, `app/modules/base.py`; `registry.get_enabled_hooks()` / `start_background_tasks()`). `hooks` maps a hook name to an async callable: the module that owns a flow documents the name, arguments and return value next to where it calls `get_enabled_hooks(name)`, and only *enabled* modules take part (in module-key order), so the owner never imports the modules built on it. The owner must survive a hook that raises. The one hook so far is `contact_form.received` (`kontaktni_formular/hooks.py`: `await hook(db, ContactSubmission) -> ContactHookResult | None`; the router calls it before it mails anything, a failing hook is logged, rolled back and skipped, and what it returns may put a `subject_tag` in front of the subjects of both mails and a `reply_to` on the sender's confirmation). The route reaches the hooks through the dependency `get_contact_form_hooks`, which a test pins to `[]` so it never depends on a branch's `modules.json`. `background_tasks` are no-argument coroutine functions started once from `main.py`'s `lifespan` when the module is enabled (and cancelled on shutdown) - the only scheduler the application has; one that raises is logged and ends, never stops the application. `email.send_email` takes optional `reply_to`, `attachments` and `headers` (never pass a `message-id` header: fastapi-mail would add it twice).
- **`articles` is the first module other modules build on** (article text, types and visibility; no dependency of its own). Tables `module_articles` / `module_article_types`. An `Article` has title, unique slug, perex (≤500), sanitized HTML `content`, image, a status (`draft` / `published` / `archived`), an optional display window (`display_from` / `display_to`, open-ended), a pinned flag and an optional type; an `ArticleType` carries four hex colours - frame and tint for the light and for the dark theme (the frontend draws a typed article through CSS custom properties, `articles.css` picks the pair under the class-based `.dark`). **`app/modules/articles/visibility.py` is the one place visibility lives**: `listed(today)` (published and inside the window as of today) is what listings and walls show; `findable(today)` (listed or archived - archived articles are out of the listings but stay reachable through calendars, archives and search, window ignored) is what search uses; drafts are in neither. Modules built on articles import these two conditions instead of restating them. The detail page (`GET /{slug}`) serves published and archived articles regardless of the window (the window governs what is *listed*, not whether a link someone has keeps working); a draft is 404 there and previewed through `/manage`. Search runs on `Article.search_text`, rebuilt on every save from title, perex and the plain text of the content, lowercased and without diacritics (`search.py`; the query is normalized the same way, so "krava" finds "Kráva", and every word must match; LIKE wildcards are escaped) - no database extension involved. Images upload to `Settings.uploads_dir`/`articles/` (magic bytes checked, 5 MB, generated names, public `GET /uploads/{filename}`); a type in use can only be deleted with `?replace_with=<other type id>`. Everything under `/manage` is `require_admin`; there is no DELETE for articles (archive instead). Frontend: `/articles` (list, search, type filter), `/articles/:slug`, `/articles/manage[/new|/:id|/types]` (gated on `useAuth().user.is_admin`; the backend checks on every request regardless); `ArticleCard` and `typeStyle()` are exported for applications' own pages; the article page renders the `article.detail` slot (context `{ article }`) and the editor of a *saved* article the `article.editor` slot (context `{ article }`).
- **`event_calendar` builds on `articles`** (`manifest.requires = ("articles",)`): an `Event` (table `module_events`) is only a *term* belonging to exactly one article (`article_id`, `ON DELETE RESTRICT`; an article can have any number of events): a title (defaults to the article's in the editor form), a `short_description` of at most 128 characters (what the calendar shows when you point at or focus the event), `start_date`, an optional `end_date` (a run of days), optional `start_time` / `end_time` (`end_time` only with a `start_time`; within one day not before it - checked by the schema, the router against the merged stored values on PATCH, and by two `CHECK` constraints). An event has no page, slug, image, status or pinned flag of its own: it leads to its article, is drawn in the colours of the article's type, and **is visible exactly when its article is** (`articles.visibility`; never restated here). `GET ""` (the upcoming list: events not yet finished, soonest first, paged by `page_size`) shows `listed` articles' events; the month calendar (`/month`, multi-day events appear on every day they cover), the archive tree (`/archive`, by the month an event *starts* in), `/by-article/{id}` and `/search` use `findable` - archived articles keep their dates in the calendar and in search. **`GET /dashboard` is the wall** and is made of *articles*: `upcoming` is the article with the nearest event that has not finished (an article is "upcoming" while it has one, "past" afterwards), `pinned` the other pinned ones (newest date first), `recent_past` the last five unpinned ones without an upcoming event; each item carries the `date` it is sorted by - its nearest upcoming event, else its latest one (`date_kind: "event"`), else, for an article with no events, the day it was created (`"created"`). `/search` returns articles to open: matches in the article's text (the articles module's diacritics-insensitive search) or in any of its events' `search_text` (title + description, normalized the same way, rebuilt on every save) or start date (`DD.MM.YYYY` / `YYYY-MM-DD`). Deleting an event is a real delete (the article stays); a `409` answers when something built on events refers to it (`ON DELETE RESTRICT`). The migration `events_belong_to_articles` **drops and recreates** `module_events` - the old events were deliberately not carried over. Frontend: `/events` (upcoming list, month listing via `?year=&month=`, calendar and archive tree), `/events/manage[/new|/:id]` (`/events/manage/new?article=<id>` preselects the article); `EventCalendar` and `EventCard` are exported for applications' own pages, together with the `Dashboard` / `DatedArticle` types of `/dashboard`. Slots: it **defines** `event.actions` (after each date on the article page, context `{ event }`), `event.manage` (in each row of the administrators' event list, context `{ event }`) and `event.editor` (below the form of a *saved* event, context `{ event }`) for modules built on events, and **contributes** the article's dates to `article.detail` and a panel to add / edit / delete them to `article.editor`.
- **`forms` is infrastructure for other modules** (no dependency of its own, **no public route**, no nav entry): forms with questions of seven types (`checkbox`, `radio`, `text`, `number`, `date`, `time`, `datetime`; answers are JSON - a list of option ids, an option id, a string, a number, `YYYY-MM-DD`, `HH:MM`, `YYYY-MM-DDTHH:MM`), tables `module_forms` / `module_form_questions` / `module_form_submissions`. A module that owns a form uses **`app.modules.forms.service`**: `create_form`, `replace_questions`, `get_questions` + `to_logic_questions`, `validate_answers` (pure; returns the snapshot to store, raises `FormValidationError` whose `errors` map a question id to a short **error code** - `required`, `too_short`, `pattern`, `before_min`, ... - that the frontend turns into the visitor's language, `as_detail()` is the shape for the consumer's 422), `store_submission` (flush only, so it shares the consumer's transaction), `list_submissions` / `compute_stats` (both take optional `submission_ids`, so a consumer shows and summarises only the answers that still count - e.g. a registration drops its cancelled ones), `delete_submissions` and `delete_form` (`FormInUseError` while answers exist: `form_id` on a submission is `ON DELETE RESTRICT`, deliberately no cascade). **All rules live in `logic.py`, pure and database-free**: which questions are shown (`visible_questions`), validation, statistics (`stats_from_answers`); the semantics - conditions are ANDed, refer only to an EARLIER question, a hidden question counts as unanswered so hiding chains, `not_equals` / `not_contains` are true while unanswered, text compares trimmed and case-sensitive - are in its docstring. **A submission is a snapshot of the whole form as worded when answered**: one entry per question `{question_id, position, label, type, shown, value, display, options}`; answers to a hidden question are neither validated nor kept (`shown: false`, so statistics can tell "not shown" from "left blank"), and editing or deleting a question later changes neither how an answer reads nor the statistics (grouped by question id and type, the latest wording wins, an option no longer on the form keeps its old name). A form's questions are saved as **one ordered list** (`PUT /manage/{id}/questions`: update known ids, insert new, delete the missing; the client chooses the ids because conditions refer to them; an id of another form is a 409) and checked as a whole (config per type, conditions only on earlier questions with an operator and value that suit the source). **Regular expressions** (text questions) are the one risk an administrator hands to strangers: Python's `re` has no timeout and would block the event loop, so matches use the **`regex` package with a timeout** (`REGEX_TIMEOUT_SECONDS`; already in `requirements.txt`, no new dependency), a pattern is limited to 200 characters and an answer to 2000, the whole answer must match, and a pattern that does not get through a few adversarial probe strings in a few milliseconds when the form is saved (catastrophic backtracking) is refused with a 422. The administrators' API (`/manage`: create, get, replace questions, delete, `submissions` paged newest first, one submission, `stats`) is entirely behind `require_admin`. Frontend: `FormBuilder` (editor; blocks saving while a condition no longer holds), `FormRenderer` (+ `collectAnswers()` from `values.ts`: only shown, answered questions, numbers as numbers), `SubmissionList`, `SubmissionView`, `FormStats` (bars drawn with plain CSS, the numbers always written out) - the viewing components take their data as props - and one page, `/forms/manage/:formId` (answers and statistics of every answer of a form; the module has no list of forms, modules that use one link there). **The condition logic exists twice**: `frontend/src/modules/forms/conditions.ts` is a literal translation of `logic.py`, and `backend/tests/data/forms_visibility_vectors.json` is what keeps them equal - the backend suite checks `logic.py` against it, and the frontend (no test runner, none to be added without asking) is checked by hand, from the repository root, with node (it runs the TypeScript directly): `node --input-type=module -e "import {readFileSync} from 'node:fs'; import {visibleQuestions} from './frontend/src/modules/forms/conditions.ts'; const v=JSON.parse(readFileSync('backend/tests/data/forms_visibility_vectors.json','utf8')).vectors; const bad=v.filter(x=>JSON.stringify(visibleQuestions(x.questions,x.answers).map(q=>q.id))!==JSON.stringify(x.visible)); console.log(v.length-bad.length+'/'+v.length+' vectors pass', bad.map(x=>x.name)); process.exit(bad.length?1:0)"`. Change one side, change the other, add a vector.
- **`event_booking` builds on `event_calendar` and `forms`** (`manifest.requires = ("event_calendar", "forms")`; ships disabled): registration for events. Tables `module_booking_registrations` / `_blocks` / `_bookings` / `_changes`. A `Registration` belongs to **one** event (`event_id` UNIQUE, `RESTRICT`), owns a form (`form_id`, created with it through `forms.service.create_form`, deleted with it) and has an access mode - `public`, `authenticated`, or `link` (a registration reached by link is **not mentioned** by any public endpoint without `?token=<link_token>`: the same 404 as one that does not exist) - a default `capacity` and `is_open`. **Slots are never stored**: `slots.py` (pure and database-free, "now" passed in) expands a registration's *blocks* - days (`dates` / `weekdays` within a range / `any_future`), times (`all_day` / `manual` / `generated`), an optional capacity of their own - with `expand_slots`; no blocks means every future day, all day; the same slot in two blocks is offered once with the FIRST block's capacity; an all-day slot has one capacity per day; the past and anything beyond `max_days_ahead` are never offered; `validate_blocks` refuses what makes no sense (an all-day and a timed block on one finite day, ...). Times are local, Europe/Prague (`zoneinfo`; `tzdata` is in `requirements.txt`, and without a time zone database `local_now()` falls back to the server clock with one warning). **Capacity is guarded by a row lock, not a constraint** (a slot can hold many): everything that puts a confirmed booking into a slot - a visitor booking, an administrator moving one - first takes `SELECT ... FOR UPDATE` on the REGISTRATION row (always before touching a booking, so two requests cannot deadlock), counts, then writes; `tests/test_modules_event_booking_concurrency.py` fires `asyncio.gather` at one place with real commits (its rows are removed by id; it never clears tables). **When registering is possible**: the registration `is_open`, its article `listed` (an archived one stays visible, but closed), the event not over, the slot in the future. `service.py` never commits and every check that can refuse comes before the first write, so a refusal leaves nothing behind; refusals are `BookingError` (an `HTTPException`) whose 422 / 409 detail is `{"errors": {field_or_question_id: code}}`, the shape forms uses. A booking carries `language` (the one it was made in - every later e-mail, also after an administrator's change, is in it), a `cancel_token` (the public page `/bookings/cancel/:token` shows the booking and a Cancel *button*; cancelling is a POST, never a GET, since a mail client or a bot may open the link; it is idempotent) and a `submission_id` (the answers as a forms snapshot). Spam: a honeypot field `fax` (filled in = told "created", nothing stored) and at most `max_active_per_email` upcoming bookings per address per registration; **there is no rate limiting** in the core or in this module. The optional user for `authenticated` access is the module's own `deps.get_optional_user` (`get_current_user` is untouched; an unusable token counts as none, so a public registration still works and a signed-in-only one answers 401). The administrators' API (`/manage`, every route `require_admin`; `tests/test_modules_event_booking_admin.py` walks each one as anonymous and as a non-admin and **fails when a route is added outside `/manage`** without being listed as public) manages registrations (blocks are replaced as a whole list; a registration with any booking - cancelled ones too - answers 409 on delete; `regenerate-link`; `preview-slots` is the editor's live preview, computed by the function that serves the visitors), lists and filters bookings, exports CSV (UTF-8 with a BOM, `;`, every cell through `csv_cell` against formula injection), summarises the answers of the CONFIRMED bookings, and **changes one booking**: `PATCH /manage/bookings/{id}` (slot, name, e-mail, answers - a new slot passes the same rules and the same lock, and the administrator does **not** override capacity: 409 when full, 422 when it does not exist; answers are re-validated and stored as a new snapshot; nothing actually changing is a 422) and `POST /manage/bookings/{id}/cancel`, each with an optional note (up to 1000 characters; it goes in the e-mail and the history, never on the public page) and `notify` (default on). Every change writes a `BookingChange` - only the fields that changed, for answers just which questions - and whether the e-mail went out: **a failed e-mail is logged, recorded in `email_error` and reported as `email_sent: false`, and the change stands**. The e-mail texts and switches are in `backend/modules/event_booking.json` (the `kontaktni_formular` pattern: validated on load, placeholders restricted, `{note_section}` = a localized heading and the note, or nothing; a test guards the committed file); `BOOKING_NOTIFY_MAIL` (else `CONTACT_MAIL`) is where the notice about a new booking goes. **Retention** (`retention_months`, default 12): `purge_expired(db, today)` deletes old bookings with their answers and history; there is no scheduler, so `maybe_purge` runs it at most once a day per process when a booking is made or the administrators' list is opened, and `POST /manage/purge` runs it on demand. Frontend: the booking panel goes into the calendar's `event.actions` slot (a day from a list when every block is a list of days, otherwise a month calendar showing only days with room; then the times; then name, e-mail, consent, the honeypot and the questions through `FormRenderer`), `event.manage` gets a link per row and `event.editor` the "Registration" panel (`BookingsAdmin`: the table, one booking's detail with its history, edit, cancel, the summary); routes `/bookings/cancel/:token` and `/bookings/manage[/new|/:id]` (no nav entry). A visitor who has to sign in goes through `src/utils/returnPath.ts` (`rememberReturnPath` / `consumeReturnPath`: sessionStorage, 30 minutes, same-site paths only), which `AuthContext.login`, the consent redirect and `OAuthCallback` honour, so they come back to the article. `usePageMeta`'s `noindex` is passed through `useNoindexMeta` in the module's `ui.tsx` (a cast, so it also builds where an older `usePageMeta` lacks the parameter).
- **`tickets` is an administrators-only ticketing module** (ships disabled; no `requires`: it stands on its own and extends the contact form and the CRM only while they are enabled). Tables `module_tickets` (`number` is an identity column starting at 100001 - what people see and what replies are matched by; `type` `general` (default) / `issue` / `order` / `internal`, `status` `open` / `closed`, `source` `manual` / `email` / `contact_form`, the requester's name and e-mail, `partner_id` -> `module_crm_partners` `ON DELETE SET NULL`), `module_ticket_entries` (the thread: `kind` `note` (internal) / `incoming` / `outgoing`, sanitized `content_html`, `minutes` spent, an author label taken from the token, `message_id` unique so a mail is never filed twice, `seq` to order entries of one instant) and `module_ticket_attachments`. The header's total time is computed (sum of the entries' minutes), never stored. Everything under `/manage` is `require_admin` (the local `is_admin` flag, as in the CRM) and tickets are addressed by their number; `tests/test_modules_tickets_access.py` walks every route as anonymous, as a non-admin and as an administrator and fails when a route is added outside `/manage` without being listed. The one public route is `GET /files/{name}`: pictures inside entries (pasted in the editor or sent inline in a received mail) must load for the editor and for the requester's mail client without signing in, so they live at an unguessable name (uuid4 hex + image extension; the route serves only names of exactly that shape, only the four image types, `nosniff`) - every other file is private (`<hex>.bin`, no address, downloaded through the admin route with the bearer token, mailed as a real attachment). Uploads (`POST /{number}/images|attachments`, 5 / 10 MB) are validated like the articles' (magic bytes) and linked to an entry by `attachment_ids` when the entry is created; an unused file can be taken back. **Three sources** go through `service.py`: a ticket typed in by an administrator (`POST /manage`; the CRM partner is linked only when chosen, and only while the CRM is enabled - `service.crm_enabled()` reads `modules.json`), a mail read from the mailbox, and the contact form (the manifest's `contact_form.received` hook creates the ticket and returns `[Ticket#N]` and the mailbox address, so the owner's notification and the sender's confirmation both carry the number and the confirmation's Reply-To is the mailbox). **A mail we send** (an `outgoing` entry; sent *first*, a transport failure answers 502 `email_failed` and saves nothing, so the text can be sent again) has the subject `[Ticket#100253] - <title>` and `Reply-To` = `service.mailbox_address()` (`TICKETS_MAILBOX_ADDRESS`, else the IMAP user name if it is an address, else `MAIL_FROM`, none while no mailbox is configured). **A mail we receive** (`service.import_message`, `mailparse.py` is pure and standard-library only): matched to its ticket by the number in the subject (`TICKET_TAG`, tolerant of spaces and `Re:`), else a new ticket whose requester is the sender and whose partner is looked up by the sender's address when the CRM is on (case-insensitive exact match, active before archived, then oldest; none found = no link); a reply reopens a closed ticket; skipped, with the reason logged, when its Message-ID was filed already, when it comes from our own address (`MAIL_FROM`, the mailbox - the owner's notification would otherwise come back as an entry) or when it is automatic (`Auto-Submitted`, `Precedence: bulk`, `List-Id`, ...) and names no ticket; the HTML is sanitized after `<div>` becomes `<p>` and `cid:` pictures are stored and re-pointed at the public address. **The mailbox** (`mailbox.py`): `TICKETS_IMAP_*` / `TICKETS_POLL_SECONDS` / `TICKETS_MAILBOX_ADDRESS` in `.env` (secrets and per-server, so not in a module config file; no `backend/modules/tickets.json` exists), stdlib `imaplib` in a thread, `BODY.PEEK` and `\Seen` only after the mail was filed, a mail that fails is retried up to 5 cycles and then flagged and given up on, one process polls at a time (a transaction-scoped Postgres advisory lock), the periodic check is the manifest's `background_tasks` entry and `POST /manage/mailbox/poll` / `GET /manage/mailbox` (status, never the credentials) are the "check now" button's. There is no automatic acknowledgement of a mailed-in request and no quoted-reply trimming. Frontend: `/tickets` (list, filters, mailbox bar), `/tickets/new` (`?partner=<id>` preselects), `/tickets/:number` (header, thread, composer: `RichTextEditor` with picture upload, attachments, the time as `90` / `1:30` / `1h 30m`, note or e-mail mode); the header icon is a `headerWidget` for administrators, and the module contributes `PartnerTickets` to the CRM's `crm.partner` slot (rendered by `PartnerPage`, defined there). The CRM's partner picker uses the CRM's own `GET /partners?q=`.
- **The shared rich-text editor and sanitizer.** `src/components/RichTextEditor.tsx` (TipTap) offers headings 1-5, bold/italic/underline/strike, font family/size/colour, text alignment, lists, quote, tables, horizontal rule, code block, links, image upload, @-mentions, YouTube/Vimeo video links (a custom `video` node in `videoEmbed.ts`, which also holds `parseVideoUrl()`) and a raw HTML source mode. `backend/app/services/sanitize.py` is applied on **every server-side write** of editor HTML and must stay in step with it: it keeps exactly the tags/attributes/style properties the editor produces, lets an `iframe` through only for `https://www.youtube-nocookie.com/embed/<11 chars>` and `https://player.vimeo.com/video/<digits>` (with a short plain query) and forces `loading`, `referrerpolicy` and `sandbox` on it. So "full access to the HTML source" means every *allowed* tag - script, event handlers, other-origin frames and `url()` styles are removed on save whatever was typed, and the source mode's hint says so. Adding a TipTap extension means adding its output to the sanitizer (and a test in `tests/test_sanitize.py`) in the same change.
- A real module is free to diverge from this contract in its own app-specific ways once created (extra files, its own sub-router structure, etc.) — the only hard requirements are the `manifest`/`ModuleDefinition` shape discovery depends on and the `key` match. Building actual modules (administration, reservations, orders, ...) belongs on `core` if they're broadly reusable, or directly on an application branch if they're one-off.

### File headers
Every hand-written source file (backend `.py` under `app/`, `tests/`, `alembic/`; frontend `.ts`/`.tsx`/`.css`) starts with the project header — a `#`-comment block in Python, a `/** ... */` block in TS/TSX/CSS:
```
Part of the With FBraun project template.
Author: František Braun <frantisek.braun95@gmail.com>
Freely available as a template for building custom applications.
```
It goes as the very first lines of the file — after a shebang if one exists, or before a `.d.ts` file's triple-slash reference directive, or above (never inside) an Alembic migration's auto-generated revision docstring, since Alembic's own tooling reads that docstring verbatim. Add it to new files as you create them.

### Deployment (`scripts/`)
- `build.py` archives `backend/` / `frontend/` / `scripts/` from a git ref (a `B-`/`F-` tag in STABLE mode, `HEAD` in SNAPSHOT mode), builds the frontend with `npm install && npm run build`, and uploads the resulting zip to FTP per `scripts/build.config.toml` (gitignored; copy from `.example`). For STABLE backend/frontend builds it first seals that component's `release_news.json` under the resolved version (see Cross-cutting above) — commit the sealed file and create the release tag from that commit before running the build, or the archive won't include it.
- The frontend build's `.env` is **the development directory's own `frontend/.env`, copied as it is stored** (`copy_frontend_env()` in `build.py`) next to the sources extracted from the git ref - the build writes no `.env` of its own, and `build.config.toml` no longer has a `client_api_key`. The file is untracked, so (like `backend/.env` in `build_scripts()`) it is always the current local one, never one from the ref. Vite bakes its values into the static bundle, so before a build that is going to a server, `frontend/.env` must hold that server's addresses (`VITE_API_URL`, `VITE_APP_URL`, `VITE_AUTH_URL`); the build stops with guidance when the file is missing, prints the variable names (never the values) and warns - but still copies - when a `*_URL` points at localhost, which is what a development `.env` usually has. **A real application must never send its API key from the browser** (see the BFF note under Authorization above): `VITE_API_KEY` is a leftover of the template's own demo build, which has no backend-held key to proxy through - don't put a real app's key into `frontend/.env`, `.env.example` or anywhere else client-side.
- `install.sh` / `upgrade.sh` are Linux-only systemd + nginx deployment scripts (require `psql`, `nginx`, `systemctl` on `PATH`) driven by `scripts/deploy.config.sh` (gitignored; copy from `.example`). They provision the Postgres role/DB from `backend/.env`'s `DATABASE_URL`, and health-check via `GET /api/public/version` after `upgrade.sh` restarts the service — a change that breaks that endpoint will trigger `upgrade.sh`'s automatic rollback. `build_scripts()` bundles these together with the current, real `backend/.env` — unlike the backend/frontend archives (built from a git ref), this bundle always reflects the current local filesystem and is never meant to be redistributed as part of the template, only pushed to this project's own live server.
